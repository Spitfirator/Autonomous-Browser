\chapter{Introduction}
\label{chap:introduction}

\section{Motivation}

Large language models increasingly operate as agents: they observe an
environment, choose tools, inspect the result, and continue until a task is
complete. Browser agents apply this loop to navigation, form entry, file
handling, and web applications in which a model output can become an external
side effect. This capability is useful precisely because web tasks are rarely
one-shot questions: benchmarks such as WebArena require agents to carry state
across several dependent interactions~\cite{zhou2024webarena}.

The same loop creates a security problem. Indeed, web observations mix application
content, user-generated data, embedded resources, and text controlled by an
attacker. An indirect prompt injection places instructions in that data so the
agent encounters them while pursuing a legitimate goal~\cite{greshake2023indirect}.
The attack does not depend on a malformed API call, it exploits an authority
ambiguity: the model is expected to understand novel page content, yet must
also decide
whether that content is entitled to redirect its behaviour. Once the model can
invoke privileged tools, a successful redirection can change remote state or
disclose information instead of producing incorrect prose alone.
Prompt reminders, delimiters, and detection combined with removal can reduce
exposure~\cite{yi2025bipia,hines2024spotlighting,chen2025detectremove}, but these
mechanisms do not by themselves provide an independent check at privileged
execution. Throughout this dissertation, the \emph{operator} is
the human task owner who supplies the goal and whose browser authority the
agent exercises. Classical protection principles, such as complete mediation
and least privilege, suggest a different allocation of responsibility: the
former places a check at each privileged use, while the latter limits which
component may perform the effect~\cite{saltzer1975protection}. For an agent,
this means the model can remain a
flexible planner without being the final authority for its proposed actions.
An independent runtime can enforce deterministic constraints, control data
flows, request narrowly scoped authority, and record the outcome.

\section{Research question and thesis}

The research question is:

\begin{quote}
\textbf{RQ.} \rqone
\end{quote}

Security and utility are evaluated together. A system that blocks every action
can suppress attacks while destroying the purpose of an agent; conversely,
high task completion is not useful if trajectories also achieve attacker
goals. The dissertation therefore measures native user-task success, native
attacker success, their joint outcome, and whether attacker-directed actions
reach the executor.

The thesis is that \emph{independent runtime enforcement can reduce evaluated
policy violations while preserving useful autonomy under the tested
conditions}. Independence refers to where enforcement authority resides. The
evaluated planner also receives fixed security guidance, which may influence
its proposals; however, allow, block, approval, takeover, and execution
decisions remain outside the acting model. The claim is tied to defined tool and
browser benchmarks; it does not extend to prompt injection in general.

\section{Approach}

This dissertation presents \systemname, a local research prototype positioned
between a BrowserUse agent and its privileged executor. Sentinel intervenes at
two points in the agent loop. First, before inference, an observation guard
identifies untrusted browser, extraction, and tool-result regions and checks
them for configured prompt-injection signals. When sanitisation is enabled, the
guard removes attributable regions and then scans the exact reconstructed model
input again. Second, immediately before execution, an action guard rebuilds the
live browser context, classifies capabilities and sensitive data, and considers
the origin of earlier untrusted observations. Only a proposal allowed by the
central policy engine can then reach the executor.

Alongside these automatic controls, Sentinel gives the operator selective
rather than unrestricted authority. Hard policy and protected data flows remain
non-overridable. Where policy permits review, a consequential proposal may
receive narrow, expiring approval; even then, Sentinel evaluates it again
against the live state before execution. By contrast, recognised credentials,
one-time codes, payment data, and other protected values trigger a direct human
step, so the operator acts in the page instead of authorising the agent to type
the value. Similarly, if a suspicious current-page observation cannot be
sanitised and verified, Sentinel withholds it. The operator may inspect the
page, but the agent continues only from a fresh observation. A Chrome extension
presents these states and the redacted decision history, while the server
remains the source of authority.

The evaluation follows the same progression from controlled tool use to browser
trajectories. First, AgentDojo supplies tool-agent tasks with built-in checks for
user-task and attacker-goal success across four application domains
~\cite{debenedetti2024agentdojo}. The second stage evaluates Sentinel with a
BrowserUse agent~\cite{muller2024browseruse} in the mutable GitLab and Reddit
environments supplied by WASP~\cite{evtimov2025wasp}, thereby adding observation
construction, navigation, and browser re-planning. The principal browser study
repeats the 84-case matrix across three seeds under the off, policy-only, and
full conditions. This staged design first tests whether the approach transfers
to a browser loop and then estimates the additional effect of configured
sanitisation within a shared scaffold. In particular, policy-only and full use
the same fixed security guidance and action controls:
policy-only retains detected content and adds a detection-specific warning,
whereas full removes attributable content and continues only when the
reconstructed observation passes re-detection. The final contrast therefore
includes the accompanying suppression of that warning.

\section{Contributions}
\label{sec:contributions}

The dissertation contributes an implemented answer to the authority problem,
not a new browser agent. Its three contributions build on one another.

\begin{enumerate}
  \item \textbf{A practical enforcement boundary for an existing browser-agent
  loop.} Sentinel governs the exact input seen by the model and every privileged
  action proposed to the executor. It reads live browser context, applies one
  central policy, fails closed when required context is missing, and records
  paired attempted and terminal outcomes. Thus, the model can continue to plan
  dynamically, but it cannot authorise its own actions.

  \item \textbf{An end-to-end workflow for untrusted observations and selective
  authority.} When Sentinel can safely attribute a finding to an untrusted
  region, it removes that region, reconstructs the observation, and continues
  only if a second detection pass is clear. If automatic enforcement cannot
  safely continue, the operator can review a narrowly scoped request, perform
  a protected step directly, or resolve an observation incident. The extension
  presents those choices, while the server alone validates and records the
  resulting authority.

  \item \textbf{A provenance-aware evaluation of security and usefulness.}
  The three matched within-model AgentDojo comparisons provide controlled
  end-to-end evidence: between the off and governed conditions, attacker success
  fell from 20.8--32.8\% to 0--0.2\%, while utility rose from 57.6--68.0\% to
  70.9--76.8\%. WASP then tests the architecture inside a browser loop. Across
  three seeds, full enforcement reduced attacker success confirmed by the
  action audit from 17/252 to 0/252 and attacker-directed execution from 42/252
  to 0/252. Utility changed from 154/252 to 149/252, while secure utility
  (outcomes that were both useful and secure) rose from 138/252 to 149/252. The
  full-versus-policy-only comparison further isolates the configured
  sanitisation increment.
  The two studies report what happened to the user's task as well as what
  happened to the attack, so inactivity or baseline model failure is not
  mistaken for security.
\end{enumerate}

Sentinel's contribution is to bring observation governance, executor-side
policy, selective human authority, and paired audit together around a dynamic
browser agent, implement the resulting architecture, and evaluate its security
and utility.

\section{Dissertation structure}

\Cref{chap:background} introduces the prompt-injection and system-security
context, and \cref{chap:threat-model} then defines the authority boundary and
security requirements. Building on this foundation, \cref{chap:design}
