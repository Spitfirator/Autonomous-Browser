\chapter{Background and related work}
\label{chap:background}

\section{Browser agents and indirect prompt injection}

An LLM agent places a generative model in a feedback loop of goals,
observations, decisions, tool calls, and results. ReAct made the
reasoning--action interleaving explicit, while Toolformer studied how models
can learn to invoke tools~\cite{yao2023react,schick2023toolformer}. Browser
agents extend that loop to URLs, page representations, interactive elements,
downloads, uploads, and code-capable actions. WebArena and WorkArena evaluate
such agents through executable environments and state-based task oracles
~\cite{zhou2024webarena,drouin2024workarena}. Their structure highlights two
properties relevant here: success is an environmental outcome rather than a
plausible response, and observations contain data outside the operator's
control.

Prompt injection exploits the fact that instructions and data share the same
model context. Direct attacks alter the user's prompt; indirect attacks arrive
through retrieved content that the application expected to treat as data.
Greshake et al. demonstrated indirect attacks through documents and web
content, including disclosure and propagation effects
~\cite{greshake2023indirect}. A browser-agent attacker can place equivalent
instructions in a page, user-generated record, link label, or stored result.
The agent encounters them while acting with the user's delegated authority. For
example, an attacker-controlled project comment can instruct an agent that was
asked to summarise an issue to open account settings and change a security
property instead~\cite{evtimov2025wasp}. The page supplies the instruction, but
the resulting action is performed through the user's browser session.

This differs from conventional parser injection. A browser agent is
deliberately expected to understand previously unseen prose, so a fixed grammar
cannot cleanly separate every instruction from every datum. Delimiters can mark
provenance, but page text can imitate them and the model must still decide
which instruction has authority. Formalisations and benchmarks identify this
instruction--data confusion as a central mechanism
~\cite{liu2024formalizing,yi2025bipia}. AgentDojo evaluates paired user and
attacker goals in executable tool environments; WASP evaluates goal hijacking
in a browser loop and distinguishes trajectory diversion from final attacker
success~\cite{debenedetti2024agentdojo,evtimov2025wasp}. This distinction is
important because an incapable agent may achieve neither goal and therefore
appear secure under terminal attack success alone.

The current page is not the only channel. Extracted page text and tool results
can cross secondary model calls, while stored history can reintroduce hostile
content later. Multimodal agents add pixels: image-hijack work shows that
instructions embedded in images can redirect vision-language systems
~\cite{bailey2024imagehijacks}. A DOM filter cannot remove text rendered only
in pixels. Sentinel consequently treats browser-derived text and tool results
as untrusted and excludes screenshots from its evaluated interactive model
path.

\subsection{What an agent-security evaluation must measure}

Prompt-injection evaluation spans several distinct units. A detector labels a
piece of text; an action monitor labels a proposed or executed effect; an
end-to-end oracle checks whether the user or attacker changed the environment
as intended. High detector recall can coexist with a compromised trajectory if
the model is merely warned or if a dangerous effect bypasses the monitored
channel. Conversely, low terminal attack success can reflect an agent that was
diverted but lacked the capability or remaining steps to finish the attack.

AgentDojo addresses this by pairing realistic user tasks with attacker goals
in executable banking, messaging, travel, and workspace environments
~\cite{debenedetti2024agentdojo}. Its native oracles score both goals against
the resulting state. WASP applies a similar distinction to browser agents and
records whether a trajectory begins serving the attacker before the terminal
goal is achieved~\cite{evtimov2025wasp}. ST-WebAgentBench studies the broader
problem of policy compliance through Completion Under Policy and Risk Ratio
~\cite{levy2026stwebagentbench}. These metrics are complementary rather than
interchangeable: detection accuracy, risky execution, policy compliance, and
final-state success answer different questions.

This dissertation therefore treats security and utility as a joint outcome.
It reports native user completion, native attacker success, useful-and-secure
completion, attacker-directed attempts and executions, and the interventions
that changed the trajectory. The combination guards against two misleading
conclusions: calling an inactive agent secure, or calling a capable but
compromised agent useful.

\section{Defence design space}

\subsection{Model-facing defences}

Prompt instructions and provenance markers are inexpensive because they
require no new execution architecture. BIPIA evaluates reminders, boundary
awareness, in-context examples, and training across indirect-injection tasks
~\cite{yi2025bipia}. Spotlighting transforms untrusted tokens through
delimiting, datamarking, or encoding so their origin remains salient to the
model~\cite{hines2024spotlighting}. StruQ instead trains a model to distinguish
structured instruction and data channels~\cite{chen2025struq}. These methods
can reduce compliance with tested injections, but the exposed model remains responsible
for interpreting the boundary and they do not independently constrain a tool
effect.

Detection supplies an inspectable decision before exposure. Removal systems
separate attack identification from segmentation or task-conditioned filtering
~\cite{chen2025detectremove}. Their effectiveness depends on both detecting an
attack and identifying the region that can be removed without destroying the
task. Distribution shift remains fundamental: finite corpora cannot cover all
wordings, encodings, page contexts, and adaptive strategies. Targeted
optimisation has bypassed defences that performed well against fixed attacks
~\cite{zhan2025adaptive}. Sentinel therefore uses detection to govern
observations while retaining policy and pre-execution checks as separate
layers.

\subsection{System-level authority}

System-level work relocates the final decision outside unconstrained model
reasoning. CaMeL extracts control and data flow from a trusted query, confines
untrusted data to constrained processing, and enforces capabilities at tool
calls~\cite{debenedetti2025camel}. Fides applies information-flow control:
confidentiality and integrity labels propagate through planning, deterministic
policies govern tool effects, and information can be selectively hidden from
the planner~\cite{costa2025fides}. PRUDENTIA builds on Fides by making planning
policy-aware and evaluating autonomy through task completion at intervention
budgets and scripted oversight load~\cite{kolluri2026prudentia}.

Other systems choose different trusted abstractions.
AgentSpec provides a lightweight language of triggers, predicates, and runtime
enforcement actions~\cite{wang2026agentspec}. DRIFT derives a minimal function
trajectory and parameter checklist from the trusted query, validates
deviations, and masks conflicting instructions before they persist in memory
~\cite{li2025drift}. Their attack-success rates are not directly comparable:
each system changes a different part of the agent stack and is evaluated under
different policies, models, and tasks. \Cref{tab:system-comparison} therefore
compares the more durable architectural question---what each system trusts and
where that trust is enforced.

Sentinel occupies a deliberately pragmatic point in this space. It preserves
an existing free-form browser-agent loop rather than first translating the
task into a trusted program or requiring a specially trained model. The benefit
is compatibility with dynamic re-planning; the cost is that Sentinel cannot
formally prove that every permitted same-origin action advances the user's
intent. It instead contributes a bounded, implemented composition: exact
pre-model observation governance, live executor-side policy, selective human
authority, and evaluation in the browser loop those mechanisms are intended to
protect.

\section{Protection principles for agent runtimes}

The reference-monitor concept requires a mechanism to be invoked on every
protected operation, isolated from the subject it constrains, and small enough
to analyse~\cite{anderson1972computersecurity}. Complete mediation, fail-safe
defaults, and least privilege provide corresponding design tests
~\cite{saltzer1975protection}. A language model is a poor monitor for its own
effects because hostile input can influence its internal state. A wrapper at
the executor can satisfy the structural requirement that every action in its
governed tool path crosses one decision point, even though natural-language
risk classification remains empirical.

Information-flow control asks where data originated and which sinks it may
reach. Denning's lattice model formalised label-constrained flow
~\cite{denning1976lattice}. Browser-agent values are less structured: page
content becomes model context and a click can disclose information without an
explicit network API. Sentinel therefore uses a bounded dynamic model:
browser observations carry untrusted provenance, detections add injection
taint, recognised values add sensitive categories, and actions expose
capabilities such as navigation, page write, file access, and code execution.
These labels give the policy engine concrete source--sink facts to enforce at
execution time; they are operational controls rather than a formal proof that
all information flows are isolated.

Runtime enforcement also needs an authority protocol. A warning is not
automatically meaningful consent: effective human-in-the-loop security
requires that information is communicated, processed, applied, and fed back
to the system~\cite{cranor2008humanloop}. Sentinel distinguishes hard refusal,
narrow approval, direct takeover, and unresolved-observation review so that a
generic confirmation cannot weaken a non-negotiable rule. This dissertation
evaluates those states as implemented technical mechanisms, not as measured
human behaviour.

Automation research further separates what the machine decides from who
implements the action. Parasuraman et al. describe automation as a sequence of
information acquisition, analysis, decision selection, and action
implementation, each of which can be allocated differently
~\cite{parasuraman2000automation}. Sentinel applies that distinction directly:
the runtime may select a hard refusal, an operator may decide a narrow approval,
or the operator may perform a protected action while the agent remains paused.
Browser-warning studies also show that interruption design affects whether a
warning is noticed and followed~\cite{sunshine2009cryingwolf,akhawe2013warningland}.
For Sentinel, the immediate requirement is structural: each interface choice
must map to one precise server-side outcome. Whether operators choose correctly
is a separate question for human-subject evaluation.

\section{Research gap}

Prior work establishes strong approaches to learned separation, detection,
structured control flow, information-flow control, and runtime rule systems.
The remaining question addressed here is integrational and empirical: can an
independent layer wrap a dynamic browser agent at both the observation and
execution boundaries, retain useful re-planning, expose selective authority to
the operator, and reduce both terminal attacks and attacker-serving execution?
AgentDojo isolates that enforcement mechanism; WASP tests whether it survives
the additional complexity of browser observations and mutable web state.
