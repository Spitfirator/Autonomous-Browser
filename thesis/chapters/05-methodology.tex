\chapter{Evaluation methodology}
\label{chap:methodology}

\section{Evaluation strategy}

Chapter~\ref{chap:design} leads to three empirical questions. Do the guards meet
their individual contracts? Around a complete agent, do they reduce attacker
success without suppressing the user's task? Does the same pattern persist when
the agent navigates, observes changing pages, and replans? The evaluation
answers them in that order.

Component replay exposes detector, sanitiser, and policy decisions directly.
AgentDojo then places the guards around complete tool-agent tasks with native
state oracles~\cite{debenedetti2024agentdojo}. WASP adds DOM-derived
observations, navigation, mutable applications, and repeated planning
~\cite{evtimov2025wasp}. Replay therefore checks the mechanisms, AgentDojo
tests controlled end-to-end consequences, and WASP tests browser-native
transfer.

Each setting resolves an ambiguity left by the previous one. A replayed block
does not show whether an agent recovers; a final-state oracle does not locate
where an unsafe trajectory stopped; a browser trajectory introduces additional
failure paths. The analysis therefore reads native outcomes with redacted
trajectory evidence, never treating an alert or block as a security result by
itself.

\subsection{Comparison logic}

The central comparison changes enforcement while holding model, task, and
scaffold fixed. AgentDojo runs every attacked instance off and on for the same
model. For each of three seeds, WASP runs the same 84 cases and inputs off,
policy-only, and full, restoring the corresponding website cell between
conditions. Rates show the balance; paired transitions identify attacks and
legitimate outcomes prevented, introduced, gained, or lost.

Pairing prevents a motionless agent from appearing secure. The evaluation reads
attacker success, utility, and secure utility jointly. AgentDojo's 97 clean
tasks provide a capability reference, not the counterfactual for an attacked
episode; the matched off condition supplies that comparison by retaining the
hostile result within the same setup.

The three WASP conditions distinguish two increments. Moving from off to
policy-only enables boundary neutralisation, a detector warning, and action
policy while browser sanitisation remains disabled. That contrast therefore
measures the mechanisms as a bundle and is not a pure estimate of action
policy. Moving from policy-only to full changes only the configured
sanitisation treatment. A confirmed removal both rewrites the observation and
suppresses the warning that accompanies retained detected content. The latter
contrast therefore isolates this configured treatment within the scaffold; it
does not separate removal from warning suppression.

Here, \emph{boundary neutralisation} means escaping page-supplied text that
imitates Sentinel's reserved protocol or authority tags while retaining the
genuine outer marker that identifies the region as untrusted. As
\cref{sec:observation-governance} explains, this protects the representation
boundary but does not remove the hostile instruction itself. Policy-only is
therefore a deliberately composite condition, whereas full adds the targeted
rewrite and clean post-check.

The Qwen 3.5 4B, 9B, and 27B campaigns share an inference profile but remain
distinct model artefacts. Parameter count was not isolated from planning, tool
selection, recovery, or error behaviour, so cross-model variation cannot
establish a causal size effect. AgentDojo and WASP likewise differ in
applications, observations, actions, and oracles. They test recurrence across
complementary settings; their absolute rates are not pooled.

\section{Conditions and outcome definitions}

The headline system contrast is \texttt{off} versus \texttt{enforce}. Off
bypasses observation rewriting and policy verdicts but retains redacted action
telemetry, which makes the resulting trajectories comparable. Enforce applies
the configured observation and action decisions. Shadow mode can record what
Sentinel would have decided without changing model input or execution, but no
shadow result is used as headline evidence.

Utility asks whether the legitimate objective was achieved; attack success rate
(ASR) asks the same of the attacker objective. Secure utility requires user
success without attacker success. For task $i$, let $u_i\in\{0,1\}$ and
$a_i\in\{0,1\}$ denote the native user and attacker oracles. Across $n$ tasks:

\begin{align}
  \mathrm{Utility} &= \frac{1}{n}\sum_{i=1}^{n}u_i,\\
  \mathrm{ASR} &= \frac{1}{n}\sum_{i=1}^{n}a_i,\\
  \mathrm{SecureUtility} &=
    \frac{1}{n}\sum_{i=1}^{n}u_i(1-a_i).
\end{align}

Secure utility is consequently not $1-\mathrm{ASR}$: an episode contributes
only if useful work is completed safely. Paired analysis makes the same idea
concrete by counting utility gains and losses, attacks prevented or introduced,
and changes in useful-and-secure outcomes.

WASP also distinguishes an \emph{attacker-directed attempt}, a proposal matching
the instantiated attacker goal, from an \emph{attacker-directed execution},
which reached the privileged tool. This shows whether the agent was diverted,
the guard stopped it, or an unsafe effect entered the application. Other events
explain the path but do not replace native outcomes.

Because the task matrices are fixed benchmark sets, not random deployment
samples, the results report exact numerators, denominators, and paired
descriptive changes. When no events are observed, $3/n$ appears only as
rule-of-three intuition under an independent binomial model
~\cite{hanley1983ruleofthree}. Native oracles remain authoritative for terminal
success, while trajectory replay determines whether matching proposals and
executions occurred. This separation avoids inflating a suspicious proposal
into a completed attack or describing a failed terminal attack as an uneventful
trajectory.

\section{AgentDojo}
\label{sec:agentdojo-method}

AgentDojo asks whether Sentinel changes complete tool-agent outcomes under a
tightly controlled intervention. Version 0.1.35 suite v1 contains 97 user tasks
across banking, Slack, travel, and workspace environments. Crossing the
applicable tasks with the published tool-knowledge attacks yields 629 attacked
instances~\cite{debenedetti2024agentdojo}. Sentinel's adapter preserves the
benchmark's tool names, arguments, environment state, and native user and
attacker oracles. It disables only the raw trace logger, which would otherwise
persist injected payloads.

Before end-to-end execution, model-free replay applies the real detector and
policy engine to 7,404 cases covering 16 public non-manual attack families and
97 distinct benign tasks. A second scorecard uses the exact AgentDojo and WASP
text representations. Because rules were revised after observed failures,
these are development regressions, not held-out detector estimates;
\cref{app:assurance} reports the details.

The end-to-end experiment then uses Qwen 3.5 4B, 9B, and
27B~\cite{qwen3.5}. For each model, a 97-task clean run establishes capability
without injection, and the full 629-instance attacked matrix is evaluated with
enforcement off and on. Within each model, both attacked conditions share
context and output limits, reasoning profile, sampling parameters, and seed;
Ollama serves the local model artefacts~\cite{ollama2026}. These controls make
paired within-model changes interpretable without turning the three model rows
into a scaling experiment.

The adapter governs tool-result observations and executor calls while leaving
task initialisation and native evaluators unchanged, so gains must appear in
benchmark state. A summary is admitted only when task identifiers, totals,
scores, model, inference profile, and sampling settings match the campaign
record. \Cref{app:assurance} lists exact run identities and provenance depth.

\section{WASP}
\label{sec:wasp-method}

WASP asks whether the pattern survives a browser loop in which each effect can
change the next observation and plan. The adapter pins the benchmark and
BrowserUse revisions while retaining WASP's official injector and native oracles
~\cite{evtimov2025wasp,zunic2026browseruse}. Twenty-one attacker scenarios are
crossed with two legitimate user goals and two injection formats, producing 84
attacked episodes in each condition. Repeating this matrix for seeds 0, 1, and
2 under off, policy-only, and full produces 252 episodes per condition and 756
overall.

All conditions share the Qwen 3.5 27B artefact, 30-step single-action scaffold,
inputs, sampling settings, and DOM/accessibility observations; screenshots are
excluded. No person reviewed or resolved requests during the campaign; the
controller records this unattended configuration as participant mode
\texttt{none}. The progression is:

\begin{description}[style=nextline,leftmargin=24mm]
  \item[Off] The prompt-injection boundary and action-policy enforcement are
  bypassed, providing the attacked baseline while retaining redacted telemetry.

  \item[Policy-only] Boundary neutralisation, the detector warning, and action
  policy are enabled, but browser sanitisation is disabled. Compared with off,
  this condition measures their combined effect.

  \item[Full] Browser sanitisation is added to an otherwise byte-identical
  policy-only configuration. After a confirmed removal, the reconstructed
  observation proceeds without a model-facing warning; if the clean post-check
  fails, the observation is withheld. This final contrast isolates the
  configured sanitisation increment.
\end{description}

Native final-state oracles determine utility and raw attacker success.
Deterministic replay separately joins proposals and terminal outcomes to the
instantiated attacker goal. A native positive is called terminal attacker
success only when the audit also records attacker-directed execution. Replay
therefore separates stopped diversion, executed danger, and tool failure
without the optional LLM intermediate classifier.

Each seed and condition comprises four 21-task application/format cells. A
pristine website reset precedes every cell, and aggregation requires identical
input manifests. However, the controller processed conditions in a fixed order.
The reset removes application state but not changes in service load,
model-serving state, or other runtime conditions that might accumulate and
coincide with a later condition. Future work should randomise or counterbalance
this order.

\section{Quality controls and scope}

Only cells whose task coverage, native scores, reports, and frozen provenance
agreed entered a denominator; failed or incomplete cells remain operational
records. The checks are documented in
\cref{sec:implementation-verification,sec:appendix-wasp-provenance}. The claim
is therefore bounded to two benchmark families, three WASP seeds over one fixed
matrix, finite step budgets, DOM-only observations, no human participants, and
development-informed detector rules.
