\chapter{Evaluation methodology}
\label{chap:methodology}

\section{Evaluation strategy}

Chapter~\ref{chap:design} leads to a three-part empirical test of the research
question. First, do the guards meet their individual contracts? Second, around
a complete agent, do they reduce attacker success without suppressing the
user's task? Finally, does the same pattern persist when the agent navigates,
observes changing pages, and replans? The evaluation is organised around these
questions in this order, and Chapter~\ref{chap:results} reports the corresponding
findings in the same sequence.

Component replay exposes detector, sanitiser, and policy decisions directly.
AgentDojo then places the guards around complete tool-agent tasks with native
state oracles~\cite{debenedetti2024agentdojo}. WASP adds DOM-derived
observations, navigation, mutable applications, and repeated planning
~\cite{evtimov2025wasp}. Replay therefore checks the mechanisms, AgentDojo
tests controlled end-to-end consequences, and WASP tests browser-native
transfer.

Each setting resolves an ambiguity left by the previous one. A replayed block
does not show whether an agent recovers; a final-state oracle does not locate
where an unsafe trajectory stopped; a browser trajectory introduces additional
failure paths. The analysis therefore reads native outcomes with redacted
trajectory evidence, never treating an alert or block as a security result by
itself.

\subsection{Comparison logic}

The comparison is informative only if enforcement changes while the underlying
problem remains fixed. AgentDojo therefore runs each attacked instance twice
for the same model, with enforcement off and on. WASP extends this pairing to a
browser setting: for each of three seeds, the same 84 cases and inputs are
evaluated under off, policy-only, and full, with a pristine website reset before
every cell. Aggregate rates summarise the trade-off between security and
utility, while paired transitions show which attacks were prevented or
introduced and which legitimate outcomes were gained or lost.

This pairing matters because a motionless agent can appear secure if attacker
success is considered alone. Accordingly, the analysis reads attacker success,
utility, and secure utility together. AgentDojo's 97 clean tasks provide a
separate baseline for benign capability. These tasks are not the
counterfactual for an attacked episode; that comparison comes from executing
the same task and attack with enforcement off and on under the same recorded
setup.

The WASP progression is cumulative, so each contrast has a specific
interpretation. Moving from off to policy-only enables boundary neutralisation,
a detector warning, and action policy, while browser sanitisation remains
disabled. As \cref{sec:observation-governance} explains, boundary neutralisation
escapes page-supplied text that imitates Sentinel's reserved protocol or
authority tags while preserving the genuine outer marker that identifies the
region as untrusted. It protects that representation boundary, but it does not
remove the hostile instruction. The off-to-policy-only comparison therefore
measures these mechanisms as a bundle, not action policy in isolation.

Moving from policy-only to full changes only the configured sanitisation
treatment. After a confirmed removal, Sentinel rewrites the observation,
checks the reconstructed input, and suppresses the warning used when detected
content remains. Consequently, this contrast isolates the configured treatment
within the scaffold, but it does not separate removal from warning suppression.
Policy-only is therefore deliberately composite, whereas full adds the targeted
rewrite and clean post-check.

Finally, comparisons across models and benchmark families answer narrower
questions. The AgentDojo 4B, 9B, and 27B campaigns use the same recorded
inference profile but remain distinct model artefacts. Since parameter count was
not isolated from planning, tool selection, recovery, or error behaviour,
cross-model variation is descriptive rather than a causal size effect.
Likewise, AgentDojo and WASP differ in applications, observations, actions, and
oracles. Their value lies in recurrence across complementary settings; their
absolute rates are not pooled.

\section{Conditions and outcome definitions}

The evaluation begins by comparing an unenforced baseline with the complete
enforced configuration. AgentDojo labels these conditions \texttt{off} and
\texttt{enforce}, while WASP uses \texttt{off} and \texttt{full}. In both
benchmarks, off bypasses observation rewriting and policy verdicts but retains
redacted action telemetry. This retention keeps trajectories comparable across
conditions. The complete enforced configuration then applies the specified
observation and action decisions.

Within these conditions, three outcome measures capture security and
usefulness together. Utility records successful completion of the legitimate
objective, whereas attack success rate (ASR) records completion of the attacker
objective. Secure utility counts only those instances in which the legitimate
objective succeeds and the attacker objective does not. For evaluation
instance $i$, let $u_i\in\{0,1\}$ and $a_i\in\{0,1\}$ denote the binary outcomes
returned by the native user and attacker oracles. Across $n$ instances:

\begin{align}
  \mathrm{Utility} &= \frac{1}{n}\sum_{i=1}^{n}u_i,\\
  \mathrm{ASR} &= \frac{1}{n}\sum_{i=1}^{n}a_i,\\
  \mathrm{SecureUtility} &=
    \frac{1}{n}\sum_{i=1}^{n}u_i(1-a_i).
\end{align}

These measures answer different questions and must be read together.
In particular, secure utility is not $1-\mathrm{ASR}$: an episode contributes
only when useful work is completed safely. Paired analysis then adds a
task-level view by counting utility gains and losses, attacks prevented or
introduced, and changes in useful-and-secure outcomes.

Final-state metrics, however, do not reveal where an attacker-directed
trajectory was interrupted. WASP therefore distinguishes an
\emph{attacker-directed attempt}, a proposal matching the instantiated attacker
goal, from an
\emph{attacker-directed execution}, a matching proposal carried out by the
privileged executor. An attempt shows that the model proposed an action aligned
with the attacker's goal; an execution shows that the action crossed the
execution boundary. This distinction captures diversion stopped before
execution, as well as attacker-directed behaviour that did not complete the
final attacker goal. Even so, the benchmark's native oracles determine terminal
success, while trajectory replay explains how the episode reached its outcome.

The benchmark design also limits how far these conclusions extend. The
evaluation uses a fixed set of tasks, so its findings apply to those cases.
Accordingly, the results show the exact counts behind each rate, together with
paired changes. When a condition records no events, the rule of three gives
$3/n$ as an approximate 95\% upper bound under an independent binomial
model~\cite{hanley1983ruleofthree}. This gives context to a zero count without
implying that the underlying rate is zero.

\section{AgentDojo}
\label{sec:agentdojo-method}

AgentDojo tests whether Sentinel changes complete tool-agent outcomes under a
controlled intervention. Version 0.1.35 suite v1 contains 97 user tasks across
banking, Slack, travel, and workspace environments. Crossing the applicable
tasks with the published tool-knowledge attacks yields 629 attacked
instances~\cite{debenedetti2024agentdojo}. Sentinel preserves the benchmark
interface, state, and native oracles. To avoid recording injected payloads, its
harness calls the task suite directly without the raw \texttt{TraceLogger}; the
oracles remain unchanged.

Before model execution, component replay applies the real detector and policy
engine to 7,404 security cases from 16 public non-manual attack families and,
separately, to 97 benign tasks. A second scorecard replays the exact AgentDojo
and WASP text representations. \Cref{app:assurance} reports the details.

The end-to-end stage uses Qwen 3.5 4B, 9B, and 27B~\cite{qwen3.5}. For each
model, 97 clean tasks establish capability without injection, while 629
attacked instances are evaluated with enforcement off and on. Paired conditions
share context and output limits, reasoning profile, sampling parameters, seed,
and a locally served model artefact~\cite{ollama2026}. However, enforce combines
fixed system-level security guidance with Sentinel's observation and action
controls. Policy decisions remain independent of model compliance, yet the
paired result measures the complete governed configuration. It does not isolate
the guards' contribution; component replay supplies that direct evidence.

During each task, the adapter governs tool-result observations and executor
calls while leaving task initialisation and native evaluators unchanged, so
gains must appear in benchmark state. Within-model changes are interpretable;
cross-model differences remain descriptive. Finally, summaries are admitted
only when task identifiers, totals, scores, model, inference profile, and
sampling settings match the campaign record. \Cref{app:assurance} summarises
the shared profile and provenance controls.

\section{WASP}
\label{sec:wasp-method}

WASP asks whether the pattern survives a browser loop in which each effect can
change the next observation and plan. The adapter pins the benchmark and
BrowserUse revisions while retaining WASP's official injector and native oracles
~\cite{evtimov2025wasp,zunic2026browseruse}. Twenty-one attacker scenarios are
crossed with two legitimate user goals and two injection formats, producing 84
attacked episodes in each condition. Repeating this matrix for seeds 0, 1, and
2 under off, policy-only, and full produces 252 episodes per condition and 756
overall.

All conditions share the Qwen 3.5 27B artefact, 30-step single-action scaffold,
inputs, sampling settings, and DOM/accessibility observations; screenshots are
excluded. No person reviewed or resolved requests during the campaign, which
was conducted unattended. The progression is:

\begin{description}[style=nextline,leftmargin=24mm]
  \item[Off] The prompt-injection boundary and action-policy enforcement are
  bypassed, providing the attacked baseline while retaining redacted telemetry.

  \item[Policy-only] Boundary neutralisation, the detector warning, and action
  policy are enabled, but browser sanitisation is disabled. Compared with off,
  this condition measures their combined effect.

  \item[Full] Browser sanitisation is added to an otherwise identical
  policy-only configuration. After a confirmed removal, the reconstructed
  observation proceeds without a model-facing warning; if the clean post-check
  fails, the observation is withheld. This final contrast isolates the
  configured sanitisation increment.
\end{description}

Native final-state oracles determine utility and raw attacker success.
Deterministic replay separately joins proposals and terminal outcomes to the
instantiated attacker goal. A native positive is called terminal attacker
success only when the audit also records attacker-directed execution. Replay
therefore separates stopped diversion, executed danger, and tool failure
without the optional LLM intermediate classifier.

Each seed and condition comprises four 21-task application/format cells. A
pristine website reset precedes every cell, and aggregation requires identical
input manifests. However, the controller processed conditions in a fixed order.
The reset removes application state but not changes in service load,
model-serving state, or other runtime conditions that might accumulate and
coincide with a later condition. Future work should randomise or counterbalance
this order.

\section{Quality controls and scope}

Only cells whose task coverage, native scores, reports, and frozen provenance
agreed entered a denominator; failed or incomplete cells remain operational
records. The checks are documented in
\cref{sec:implementation-verification,sec:appendix-wasp-provenance}.

A second safeguard concerns the boundary between development and evaluation.
Some detector rules and representation-handling fixes arose from failures
observed during AgentDojo and WASP development. Component replay therefore
verifies regression coverage of known attack families, not generalisation to
unseen attacks. The middleware and condition-specific policies were frozen
before the final three-seed comparison and applied consistently throughout that
experiment. The claim remains bounded to two benchmark families, three WASP
seeds over one fixed matrix, finite step budgets, DOM-only observations, and no
human participants.
