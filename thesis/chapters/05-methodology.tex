\chapter{Evaluation methodology}
\label{chap:methodology}

\section{Evaluation strategy}

The design in Chapter~\ref{chap:design} frames three empirical questions of
increasing scope. First, do the individual guards satisfy their
contracts? Second, when placed around a complete agent, do they reduce attacker
success without preventing the legitimate task? Third, does the same pattern
hold when the agent navigates, observes changing pages, and replans? The
evaluation follows that progression; Chapter~\ref{chap:results} reports the
evidence in the same order.

Component replay exposes detector, sanitiser, and policy decisions directly.
AgentDojo then places those guards around complete tool-agent tasks with native
task-specific user and attacker oracles that inspect model output and
environment state~\cite{debenedetti2024agentdojo}. WASP adds accessibility-tree
observations, navigation, mutable applications, and repeated planning
~\cite{evtimov2025wasp}. Thus replay checks the mechanisms, AgentDojo measures
controlled end-to-end consequences, and WASP tests browser-native transfer.

Each stage addresses a limitation of the one before it. Replay cannot show
whether an agent recovers, while a final-state oracle cannot reveal where an
unsafe trajectory stopped; a browser trajectory introduces further failure
paths. The analysis therefore combines native outcomes with redacted trajectory
evidence and never treats an alert or block alone as a security result.

Furthermore, the three stages focus on Sentinel's observation and action
guards, not human performance. Automated tests and deterministic walkthroughs
assess the authority workflow and control plane separately. They show
whether the implemented states and control paths behave as designed, but cannot
measure operator comprehension, decision quality, usability, or intervention burden.

\subsection{Comparison logic}

A comparison is informative only when the underlying problem remains fixed as
enforcement changes. AgentDojo therefore runs each attacked instance twice for
the same model, with enforcement off and on. WASP applies the same principle in
the browser: for each of three seeds, the same 84 cases and inputs are evaluated
under off, policy-only, and full, with a pristine website reset before every
cell. Aggregate rates summarise the balance between security and utility;
paired transitions show which attacks were prevented or introduced and which
legitimate outcomes were gained or lost.

This pairing also guards against a misleading result: a motionless agent may
appear secure simply because it achieves nothing. Attacker success, utility,
and secure utility are therefore interpreted together. AgentDojo's 97 clean
tasks provide a separate baseline for benign capability, not the
counterfactual for an attacked episode. That comparison comes from running the
same task and attack with enforcement off and on under the corresponding
recorded setup.

The WASP conditions build cumulatively, which gives each contrast a specific
interpretation. The first step, from off to policy-only, adds fixed security
guidance to the model alongside boundary neutralisation, a detection-specific
warning, and action policy, while browser sanitisation remains disabled. As
\cref{sec:observation-governance} explains, boundary neutralisation escapes
page-supplied text that imitates Sentinel's reserved protocol or authority tags
while preserving the genuine outer marker that identifies the region as
untrusted. It protects that representation boundary, but it does not remove the
hostile instruction. The off-to-policy-only comparison therefore measures the
combined effect of these mechanisms, not action policy in isolation.

The second step, from policy-only to full, holds fixed security guidance,
boundary neutralisation, and action policy constant. Only the configured
observation treatment changes: after a confirmed removal, Sentinel rewrites the
observation, checks the reconstructed input, and suppresses the warning used
when detected content remains. This contrast therefore isolates the configured
sanitisation path within the shared scaffold, although it cannot separate
removal from warning suppression. Policy-only is deliberately composite,
whereas full adds the targeted rewrite and clean post-check.

Comparisons across models and benchmark families answer narrower questions.
The AgentDojo 4B, 9B, and 27B campaigns use the same recorded
inference profile but remain distinct model artefacts. Since parameter count was
not isolated from planning, tool selection, recovery, or error behaviour,
cross-model variation is descriptive; it cannot support a causal claim about
model size. AgentDojo and WASP also differ in their applications, observations,
actions, and oracles. Their value lies in the recurrence of a pattern across
complementary settings, so their absolute rates are not pooled.

\section{Conditions and outcome definitions}

The evaluation compares an unenforced baseline with the complete enforced
configuration. AgentDojo names these conditions \texttt{off} and
\texttt{enforce}; WASP uses \texttt{off} and \texttt{full}. Despite the
different labels, off serves the same methodological role: it bypasses
observation rewriting and policy verdicts while retaining redacted action
telemetry for trajectory comparison. The complete enforced configuration
applies the specified observation and action decisions.

Within these conditions, three outcome measures capture security and
usefulness together. Utility records successful completion of the legitimate
objective, whereas attack success rate (ASR) records completion of the attacker
objective. Secure utility counts only those instances in which the legitimate
objective succeeds and the attacker objective does not. For evaluation
instance $i$, let $u_i\in\{0,1\}$ and $a_i\in\{0,1\}$ denote the binary outcomes
returned by the native user and attacker oracles. Across $n$ instances:

\begin{align}
  \mathrm{Utility} &= \frac{1}{n}\sum_{i=1}^{n}u_i,\\
  \mathrm{ASR} &= \frac{1}{n}\sum_{i=1}^{n}a_i,\\
  \mathrm{SecureUtility} &=
    \frac{1}{n}\sum_{i=1}^{n}u_i(1-a_i).
\end{align}

These measures answer different questions, so none is interpreted alone. In
particular, secure utility is not $1-\mathrm{ASR}$: an episode contributes only
when useful work is completed safely. Paired analysis adds a task-level view by
counting utility gains and losses, attacks prevented or introduced, and changes
in useful-and-secure outcomes.

Final-state metrics still cannot reveal where an attacker-directed trajectory
was interrupted. WASP therefore distinguishes an
\emph{attacker-directed attempt}, a proposal matching the instantiated attacker
goal, from an
\emph{attacker-directed execution}, a matching proposal carried out by the
privileged executor. An attempt shows that the model proposed an action aligned
with the attacker's goal; an execution shows that the action crossed the
execution boundary. This distinction captures diversion stopped before
execution, as well as attacker-directed behaviour that did not complete the
final attacker goal. Even so, the benchmark's native oracles determine terminal
success, while trajectory replay explains how each episode reached its outcome.

The benchmark design also limits how far these conclusions extend. The
evaluation uses a fixed set of tasks, so its findings apply to those cases.
Accordingly, the results show the exact counts behind each rate, together with
paired changes.

\section{AgentDojo}
\label{sec:agentdojo-method}

AgentDojo tests whether Sentinel changes complete tool-agent outcomes under a
controlled intervention. Version 0.1.35 suite v1 provides 97 user tasks across
banking, Slack, travel, and workspace environments. Crossing the applicable
tasks with the published tool-knowledge attacks produces 629 attacked
instances~\cite{debenedetti2024agentdojo}. Sentinel preserves the benchmark
interface, state, and native oracles. To avoid recording injected payloads, its
harness calls the task suite directly without the raw \texttt{TraceLogger}; the
oracles remain unchanged.

Before model execution, component replay applies the real detector and policy
engine to 7,404 security cases from 16 public non-manual attack families and
separately checks 97 distinct benign tasks. A second scorecard replays the exact
text representations produced by the AgentDojo and WASP adapters. Their
outcomes and limitations are reported in
\cref{sec:component-evidence}.

The end-to-end stage uses the 4B, 9B, and 27B variants of Qwen
3.5~\cite{qwen3.5}, served locally through Ollama~\cite{ollama2026}. For each
model, 97 clean tasks assess capability without injection, while the 629
attacked instances are evaluated with enforcement off and on. Paired conditions
share the recorded context and output limits, reasoning profile, sampling
parameters, seed, and model name.

The enforce condition also adds a fixed security instruction to the model's
system prompt. That instruction may influence what the model proposes, but it
does not itself allow or block executor calls. Sentinel's external controls
operate independently: they
sanitise detected tool results and evaluate every proposed action before
execution. Since both are enabled together, the comparison measures the
complete governed configuration and cannot identify their separate effects. A
model-free replay then checks whether Sentinel's detector and policy engine
produce the intended decisions without a model in the loop.

During each task, the adapter governs tool-result observations and executor
calls while leaving task initialisation and native evaluators unchanged. Any
reported gain must therefore appear in benchmark state. Within-model changes
are interpretable, while cross-model differences remain descriptive. A summary
enters the analysis only when its task identifiers, totals, scores, model,
inference profile, and sampling settings match the campaign record.
The shared AgentDojo inference profile is recorded in \cref{app:assurance}.

\section{WASP}
\label{sec:wasp-method}

WASP then asks whether Sentinel's enforcement pattern remains effective in a
browser loop, where every action may change the observation on which the next
plan depends. The browser stage combines BrowserUse~\cite{muller2024browseruse}
with WASP's published injection and evaluation
pipeline~\cite{evtimov2025wasp}. Sentinel's adapter retains those components
and records the pinned benchmark and BrowserUse revisions. The matrix crosses
21 attacker scenarios with two legitimate user goals and two injection
formats, producing 84 attacked episodes per condition. Repeating that matrix
for seeds 0, 1, and 2 under off, policy-only, and full produces 252 episodes per
condition and 756 overall.

All conditions use the same Qwen 3.5 27B artefact, 30-step single-action
scaffold, inputs, sampling settings, and DOM/accessibility observations. They
share the BrowserUse base prompt and fixed handover guidance; screenshots are
excluded. Policy-only and full also share Sentinel's fixed security guidance.
The campaign used \texttt{participant=none}, so no human supplied an approval
or handoff decision. Against this background, the conditions form a staged
comparison:

\begin{description}[style=nextline,leftmargin=24mm]
  \item[Off] The prompt-injection boundary and action-policy enforcement are
  bypassed, providing the attacked baseline while retaining redacted telemetry.

  \item[Policy-only] Fixed security guidance, boundary neutralisation, the
  detector warning, and action policy are enabled, but browser sanitisation is
  disabled. Compared with off, this condition measures their combined effect.

  \item[Full] The fixed guidance and action controls remain in place while
  browser sanitisation is added. After a confirmed removal, the reconstructed
  observation proceeds without a model-facing warning; if the clean post-check
  fails, the observation is withheld. This final contrast isolates the
  configured sanitisation increment within the shared guidance scaffold.
\end{description}

Native final-state scores show whether the user or attacker goal was achieved,
but not how the trajectory reached it. WASP's native oracles determine final
utility and raw attacker success. A deterministic replay of Sentinel's audit
records then matches attacker-directed proposals and executions against each
task's known attacker goal. The thesis describes a native positive as terminal
attacker success only when the audit confirms a corresponding execution. This
separates attacks stopped before execution from actions that reached the
browser, while exposing failures at the tool boundary. No additional model
judges these outcomes.

Each seed and condition covers the same 84 tasks, organised as four 21-task
cells by attacker-goal variant and injection format. The benchmark resets the
website before each cell and admits results only when the input manifests
match. However, the cells ran in a fixed order. Although the reset restores
website state, conditions outside the site, such as service load or
model-serving state, may still change over time. A later condition could
therefore coincide with a different runtime environment.

\section{Quality controls and scope}

To protect the reported denominators, a cell enters the analysis only when its
task coverage, native scores, reports, and frozen provenance are mutually
consistent. Incomplete or failed cells remain as operational records but are
excluded from the results. The admission and provenance checks are documented
in \cref{sec:appendix-wasp-provenance}.

Development feedback limits what component replay can show. Failures observed
during AgentDojo and WASP development informed several detector rules and
representation-handling corrections, so replay measures regression coverage on
known attack families, not generalisation to unseen attacks. Accordingly, the
claim is limited to the evaluated models, two benchmark families,
three WASP seeds over one fixed task matrix, finite step budgets, AgentDojo's
tool interfaces, DOM/accessibility observations without screenshots in WASP,
and technical evaluation without human participants.

Within these boundaries, the next chapter reports the component, AgentDojo,
and WASP results.
