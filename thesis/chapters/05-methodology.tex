\chapter{Evaluation methodology}
\label{chap:methodology}

\section{Evaluation strategy}

No single benchmark captures both precise mechanism behaviour and the
contingencies of browser interaction. The evaluation is therefore staged.
Component replays test whether detector and policy rules behave as specified;
AgentDojo measures end-to-end outcomes in controlled tool environments; and
WASP tests whether the mechanism transfers to a BrowserUse agent operating
mutable web applications. Each stage answers a different question, so their
results are connected as evidence rather than pooled into one score.

AgentDojo provides 629 paired user/attacker combinations, exact tool calls, and
native state oracles across four domains. It isolates the enforcement mechanism
but does not exercise BrowserUse's DOM construction or navigation. WASP adds
page observations, browser actions, and re-planning over GitLab and Reddit, but
its smaller scenario set and mutable applications introduce more sources of
task failure. Evidence is therefore interpreted through four criteria:

\begin{enumerate}
  \item do the configured components behave deterministically on their defined
  corpora;
  \item does enforcement change native attacker and user outcomes in paired
  AgentDojo tasks;
  \item does the same security--utility pattern appear in the matched browser
  comparison; and
  \item which recorded interventions explain the resulting trajectories?
\end{enumerate}

A safe outcome need not be a hard block. If sanitisation prevents an injection
from shaping the next decision, the agent may simply resume the user's task.
Conversely, low attacker success with low utility is weak evidence because an
incapable agent can fail both goals.

\subsection{Comparison logic}

The unit of comparison is a benchmark task instance under a fixed model and
scaffold. AgentDojo supplies an identical attacked matrix to off and enforce;
WASP supplies identical generated inputs and resets the corresponding website
cell. This permits paired transition counts: an attacker success can be
prevented or introduced, and a user outcome can be gained or lost. Aggregate
rates remain useful summaries, but the transition counts expose whether a
security gain is accompanied by systematic task breakage.

Clean AgentDojo runs provide a capability reference rather than a no-attack
security control. They answer how often the model completes the 97 benign tasks
when no injection is present. The attacked off condition is the relevant
counterfactual for enforcement because it retains the hostile tool output and
otherwise uses the same model and task. Results are consequently compared
within model. Differences between 4B, 9B, and 27B are descriptive: model size,
checkpoint behaviour, and task capability change together, and the campaigns
do not support a claim that parameter count causes security.

The browser evaluation adds an implementation-transfer question. It does not
seek to reproduce AgentDojo's absolute rates: the applications, attacker
objectives, observation representation, action space, and native oracles all
differ. Agreement means that the direction of the joint security--utility
effect and the recorded mechanism remain consistent when the enforcement layer
is composed with a browser agent.

\section{Conditions and outcome definitions}

The headline comparisons use \texttt{off} and \texttt{enforce}. Off bypasses
observation and verdict enforcement while retaining redacted action telemetry.
Enforce applies sanitisation and policy outcomes. A shadow mode records
would-be decisions without changing execution, but it is not a headline row.

For task $i$, let $u_i\in\{0,1\}$ be the benchmark's native user oracle and
$a_i\in\{0,1\}$ its native attacker oracle. For $n$ tasks:

\begin{align}
  \mathrm{Utility} &= \frac{1}{n}\sum_{i=1}^{n}u_i,\\
  \mathrm{ASR} &= \frac{1}{n}\sum_{i=1}^{n}a_i,\\
  \mathrm{SecureUtility} &=
    \frac{1}{n}\sum_{i=1}^{n}u_i(1-a_i).
\end{align}

Secure utility records successful user work without attacker success. It is
not $1-\mathrm{ASR}$, which would classify an inactive agent as secure
regardless of usefulness. Matched analysis also counts utility gains and
losses, attacker successes prevented and introduced, and secure-utility
transitions.

WASP adds two task-level trajectory indicators. An
\emph{attacker-directed attempt} contains at least one proposed action matching
the instantiated attacker goal. An \emph{attacker-directed execution} requires
such an action to reach the privileged tool. These measures expose partial
compromise that does not satisfy the final-state oracle; they are task-instance
indicators rather than raw action totals. Mechanism telemetry includes
detections, sanitisation outcomes, blocks, approvals, handovers, and action
completion.

The task sets are fixed benchmark matrices rather than random draws from a
defined population, so the analysis emphasises exact denominators and paired
descriptive effects. For zero events, the rule-of-three value $3/n$ is used
only as intuition for residual uncertainty under an independent binomial model
~\cite{hanley1983ruleofthree}.

Native benchmark oracles determine terminal outcomes; Sentinel telemetry does
not relabel them. Conversely, the trajectory replay does not infer attacker
success from the final state. It asks the narrower question of whether a
proposal or execution matched the instantiated attacker goal. Reporting both
layers prevents a failed final attack from erasing an unwanted intermediate
effect, while retaining the benchmark's own environmental ground truth as the
primary endpoint.

\section{AgentDojo}
\label{sec:agentdojo-method}

AgentDojo 0.1.35 suite v1 contains 97 user tasks across banking, Slack, travel,
and workspace environments. Crossing these tasks with its published
\texttt{tool\_knowledge} attacks produces 629 security cases
~\cite{debenedetti2024agentdojo}. Sentinel's adapter preserves native tool
names, arguments, state objects, and user/attacker oracles. It omits the raw
trace logger because that would persist injected payloads.

The model-free replay covers the 16 public non-manual attack families: 7,404
security cases plus the 97 distinct benign tasks. It measures detector
precision/recall, security-case blocks, benign blocks, and benign approval
incidence using the real policy engine. A detector scorecard separately covers
AgentDojo and WASP text representations. Both are regression and mechanism
tests: the rules were improved after inspecting failures, so their results do
not estimate held-out attack performance. Detailed component tables are kept
in \cref{app:assurance}.

The end-to-end campaigns use Qwen 3.5 4B, 9B, and 27B
~\cite{qwen3.5}. Each model has a 97-task clean run and all 629 attacked tasks
in off and enforce conditions. A shared deterministic campaign profile fixes
context/output limits, sampling, and seed, while Ollama serves the local model
tags~\cite{ollama2026}. The rows are independent model runs rather than a
causal parameter-scaling experiment; the full profile is recorded in
\cref{app:assurance}.

The adapter is intentionally thin. It wraps the benchmark's tool calls at the
executor boundary and governs the corresponding tool-result observations, but
leaves task initialisation and the native security and utility evaluators
unchanged. This matters because a defence-specific outcome classifier could
make a benchmark look safer without changing the environment. The clean,
attacked-off, and attacked-enforce summaries are derived from the preserved
per-task reports after checking their expected task identifiers and totals.

Only campaigns with the expected task identifiers, native scores, model name,
profile, and sampling settings were admitted to the curated summaries. The
three model rows are nevertheless interpreted independently rather than as a
scaling experiment, because their preserved historical records do not all have
the same provenance depth. Exact run identities and the resulting qualification
are documented in \cref{app:assurance}.

\section{WASP}
\label{sec:wasp-method}

The WASP adapter pins the official benchmark and BrowserUse revisions and uses
the official injector and native final-state evaluators
~\cite{evtimov2025wasp,zunic2026browseruse}. The matrix crosses 21 attacker
scenarios with two benign user goals and two injection formats, producing 84
attacked instances per condition. All thesis rows use the same 30-step,
single-action BrowserUse scaffold, sampling profile, and DOM/accessibility
observation channel, with screenshots excluded. Participant mode is
\texttt{none}: no human supplies benchmark decisions. Exact context and output
limits, sampling parameters, revisions, and immutable run tags are recorded in
\cref{app:assurance}.

The principal browser comparison uses Qwen 3.5 27B in matched off and final
sanitisation-enforce conditions. Its 168 executions share the model, scaffold,
policy, middleware, step budget, generated-input manifests, and website-reset
protocol. Primary outcomes come from WASP's unchanged final-state oracles;
attacker-directed attempt/execution is a deterministic replay against the
instantiated attacker goals. The optional LLM-based intermediate classifier is
not required.

The 9B evidence records one shared off baseline followed by warning-only,
sanitisation V1, and sanitisation V2 enforce rows. Middleware changed between
these revisions, and V2 reused the frozen off baseline. This is an engineering
development sequence: it can identify the observed weakness of warnings and
incomplete multi-line removal, but it is not assigned the matched causal status
of the 27B comparison.

GitLab and Reddit are restored from pristine clones before each 21-task cell.
Checkpoint metadata binds model, policy, participant, generated inputs, and
middleware to each native score. Failed preparation is archived before one
reset and retry, and incomplete cells are never combined. A 20-step pilot is
preserved but excluded because its action ceiling motivated the frozen 30-step
design.

The 84 instances are executed as four 21-task cells, one for each combination
of application and injection format. Reporting those cells alongside the
aggregate guards against a result produced by only one site or representation.
The websites are mutable within an instance, so restoration happens before the
cell rather than after every action; the frozen input manifest then recreates
the same initial goals in the paired condition. Preparation failures, runner
exceptions, missing task artefacts, and native-score failures are distinguished
from a benchmark oracle returning zero. Only the latter is a valid unsuccessful
task outcome. Campaign completeness therefore requires all expected task
artefacts, native scores, provenance fields, and telemetry, not merely a status
flag.

\section{Technical authority checks and evidence integrity}

Current tests exercise allow, hard block, narrow approval, bounded reuse,
deny, timeout, takeover, unresolved-observation incident, fresh capture,
cancellation, live revalidation, whole-value omission, and paired action audit.
They also cover recognised secret categories across indexed input, free-text
keystrokes, page code, and bounded uploads, together with redaction of fixture
secrets and injection text. The extension is type-checked and built. These
checks establish present implementation contracts; the benchmark numbers
remain attached to their frozen versions.

Evidence is resolved in this order: curated per-run summaries; frozen native
scores, reports, and recorded provenance; the evaluation ledger; then current
implementation documentation. Generated task results are never edited by
hand, and changed model, policy, participant, scaffold, inputs, or middleware
requires a new immutable run tag. Raw authentication state, page captures,
payloads, model outputs, and campaign directories remain local.

The experiments use isolated benchmark services and no human participants or
personal behavioural data. Internal validity is supported by fixed settings,
paired inputs, cell-scoped website restoration, and explicit failure handling.
The main external-validity boundaries are the evaluated Qwen models, one seed,
two benchmark families, finite step budgets, DOM-only observations, and
detector adaptation to known corpora. These limits are considered together in
\cref{chap:discussion} rather than repeated beside every result.
