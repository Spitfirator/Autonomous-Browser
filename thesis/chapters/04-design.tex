\chapter{Design and implementation}
\label{chap:design}

\section{Design principles and architecture}

The central design challenge is to preserve a browser agent's freedom to
interpret pages, recover from errors, and choose its next step without allowing
the model to decide whether that step is permitted. \systemname\ leaves planning
to BrowserUse while governing the information that reaches the planner and the
proposals that reach the privileged executor. Four principles translate this
separation into the runtime architecture.

\begin{enumerate}
  \item \textbf{Keep authority outside the acting model.} The model can
  interpret observations and propose tool calls, but only the middleware can
  pass an allowed proposal to the privileged executor.

  \item \textbf{Mediate both sides of the agent loop.} The observation guard
  reduces known hostile influence before inference; if that influence or an
  ordinary planning error survives, the action guard constrains the resulting
  effect.

  \item \textbf{Represent consent as bounded authority.} Approval is tied to
  reviewed live context and checked again before execution. Unless a
  higher-priority rule blocks it, a proposal carrying a recognised human-only
  value is withheld for direct operator action.

  \item \textbf{Fail closed and retain accountable outcomes.} Missing
  security-relevant context, unresolved sanitisation, operator silence,
  timeout, cancellation, or malformed authority cannot become permission.
  Decisions remain inspectable without reproducing the sensitive content that
  caused them.
\end{enumerate}

Together, these principles allow BrowserUse to plan and recover flexibly, while
Sentinel decides at runtime whether each proposed action may proceed and records
the outcome. \Cref{fig:architecture} summarises this division.

\begin{figure}[!t]
\centering
\includegraphics[width=\textwidth]{figures/sentinel-runtime-architecture-v2.png}
\caption{Sentinel's two runtime guards and server-owned authority flow.}

Following the action path from left to right, the trusted task reaches the
planner, and each proposal must cross the action guard before the executor can
change the browser. Data returns along the reverse path: page and tool content
cross the observation guard before reaching the planner. Policy governs both
guards, bounded operator authority resolves their interactive states, and the
audit trail records the resulting outcomes.

The remainder of the chapter follows this governed loop through observation,
action, authority, and audit. It then explains how the Chrome extension projects
server-owned state into the browser without becoming a second source of
permission.

\section{Runtime architecture}

\subsection{Composition and supported channel}

Sentinel runs as a Python service around a standard BrowserUse agent, so the
integration does not require a separate BrowserUse fork. A model wrapper governs
the observations passed to the planner, while a tool wrapper mediates each
proposal immediately before execution. Their implementation classes,
\texttt{GovernedLLM} and \texttt{GovernedTools}, preserve BrowserUse's normal
interfaces~\cite{muller2024browseruse}.

Each task keeps its state separate, with its own budgets, findings, grants,
intervention and cancellation state, counters, and HMAC key. This separation
means that authority cannot carry into the next task, while the per-task key
prevents identical audited values from producing linkable digests across runs.

The current model-input channel is text-only: before an observation reaches the
planner, Sentinel removes images and remaining frame captures, marks
browser-derived text as untrusted, and reduces sensitive URL metadata. The
planner receives a DOM/accessibility representation that Sentinel can inspect
and rewrite. Consequently, the current design does not cover pixel-only
instructions or tasks that require visual evidence absent from that
representation. A multimodal planner would need a separate guard for visual
observations.

Sentinel has three runtime modes, which determine whether security decisions are
evaluated and applied. Off skips prompt-injection detection and makes the action
policy return allow, while still auditing redacted action attempts and terminal
outcomes. Shadow evaluates live context with the detector and action-policy
rules, but does not apply detector-driven sanitisation or the resulting policy
verdict. Instead, it records the detections and the block, approval, or handoff
that would have occurred. Enforce, by contrast, applies those results to the
live agent run: it may sanitise or withhold a detected observation, and it may
allow or block an action proposal, request approval, or require a human step.
Later chapters compare two
configurations within enforce mode: \emph{policy-only} and \emph{full}. Both use
the same model-facing guidance, boundary neutralisation, and action-policy
checks, but \emph{full} also sanitises observations. The model channel does not
change between modes: input remains text-only, tool results remain marked as
untrusted, and navigation metadata remains redacted.

Finally, Sentinel checks for cancellation around every authority wait and again
immediately before execution. Its deadlines expire before BrowserUse's outer
step timeout, so denial, silence, cancellation, or shutdown closes the pending
action.

\subsection{One governed agent step}

A BrowserUse step may contain a short, ordered action sequence, yet Sentinel
treats each action as a separate proposal with its own authority decision and
terminal audit outcome:

\begin{enumerate}[leftmargin=8mm]
  \item \textbf{Capture.} The observation wrapper separates the trusted task
  from DOM-derived state and bounded tool results, normalises the representation,
  and removes sensitive URL metadata.

  \item \textbf{Sanitise and verify.} In the evaluated full configuration,
  Sentinel rewrites attributable findings, reconstructs the provider message,
  and scans the governed untrusted regions again. A positive current observation
  proceeds only when the reconstruction is detector-clear; otherwise it is
  withheld.

  \item \textbf{Plan.} The model receives the governed representation and
  returns proposals that describe intended effects but carry no permission.

  \item \textbf{Rebuild authority.} The action wrapper records each attempt and
  reconstructs its live origin, destination, target, policy, protected-data
  classes, and taint. Policy may allow, block, request approval, or require a
  human step. Approval triggers complete preflight again, whereas a human step
  withholds the proposal for direct operator action.

  \item \textbf{Execute and close.} Only an allowed, still-valid proposal
  reaches the tool. Its audit pair closes before the next proposal; an error,
  sequence-terminating action, or URL or focus change abandons the remainder.
\end{enumerate}

This ordering matters because observation governance runs before planning: a
later block cannot undo a plan already shaped by hostile content. Action
governance then repeats for every proposal, as its page, target, policy, or data
may have changed after planning.

\section{Observation governance}
\label{sec:observation-governance}

\subsection{Untrusted regions and representation boundaries}

Sentinel distinguishes trusted task context from browser state, extractions, and
tool results, scanning only these untrusted regions for prompt injection. Before
textual tool results enter agent history, it escapes reserved protocol tags and
places the results inside an explicit untrusted wrapper.

Untrusted content can imitate BrowserUse or Sentinel prompt structure. When
prompt-injection governance is active in enforce mode, \emph{boundary
neutralisation} escapes reserved tags within recognised untrusted regions while
leaving genuine outer wrappers and ordinary DOM tags intact. Consequently,
forged syntax cannot create a trusted region or close the real one.

At the model boundary, Sentinel also withholds page titles and replaces entire
HTTP(S) query strings and fragments. For \texttt{data:}, \texttt{javascript:},
\texttt{blob:}, \texttt{file:}, and other non-web URLs, only the scheme is
retained across model, event, and trace boundaries because the opaque suffix may
contain a document, script, path, or identifier. Other telemetry retains useful
HTTP(S) context while redacting recognised sensitive values.

\subsection{Detection and attributable sanitisation}

The detector combines signals for instruction override, authority
impersonation, role reassignment, evasion, exfiltration, forged markup, and
encoded instructions. One strong signal triggers detection; otherwise, several
weaker signals are needed.
A detected origin remains tainted for the run because an earlier observation
may already have influenced the plan. Detection alerts sent to the operator
interface include the score, severity, detected signals, and origin. Instead of
a stable content hash, a run-specific digest links repeated content only within
the same run.

For a positive finding, Sentinel first removes only attributable material. A
line rule handles a self-contained instruction, a bounded window covers an
instruction split across neighbouring accessibility-tree fragments, and
structural sanitisation provides a coarser third path.

Sentinel then rebuilds and rescans the exact provider message, producing three
states:

\noindent\begin{tabularx}{\textwidth}{@{}l@{\hspace{1.5em}}Y@{}}
  \texttt{removed} & at least one attributable region changed and the
  reconstructed input is detector-clear; \\
  \texttt{residual} & the input changed but remains detector-positive; or \\
  \texttt{unattributable} & the finding could not be mapped to a region that
  could be removed safely.
\end{tabularx}

This deterministic process makes findings repeatable and removal attributable.
It does not, however, prove that the remaining input is free from every attack:
an unfamiliar formulation may evade the configured signals, and a clean
post-check means only that those signals no longer fire.

\subsection{Fail-closed unresolved content}

Under the evaluated full configuration, \texttt{removed} is the only outcome
from a positive detection that may continue to the planner. The planner receives
the rewritten observation without a warning, although every action it later
proposes remains subject to policy.

If the current observation is \texttt{residual} or \texttt{unattributable},
Sentinel stops the process before the model call: it replaces the observation
with a fixed marker, withholds the prompt, and opens an observation incident, so
the provider never receives the unresolved content. When the operator requests
a re-check, Sentinel discards the held prompt and captures the page again;
quarantined input is never reinterpreted as approved.
Later, \Cref{fig:unresolved-observation} shows how this fail-closed state
appears to the operator when an unattributable observation is withheld.

Bounded extractions and persistent tool results need a different fallback
because pausing can cause a nested call to expire or reopen the same historical
incident. In those cases, Sentinel omits the entire affected value instead of
preserving it for another attempt.

Together, these controls reduce known hostile influence, but they cannot
guarantee that the resulting plan is safe or correct. The action guard therefore
evaluates every resulting proposal independently before execution.

\section{Action governance}
\label{sec:action-governance}

\subsection{Pre-execution reconstruction}

An action's context can change after planning: a redirect may move the browser
to another origin, a re-render may replace the target, and a local file or
policy may be updated. Sentinel therefore reconstructs the live context and
waits until the effect is concrete to decide whether the proposal may proceed,
immediately before the privileged tool is called.

Each proposal begins an auditable transaction in which Sentinel assigns an
identifier and records \texttt{attempted} before preflight. A guarded completion
routine then adds exactly one terminal outcome, so executions, blocks, denials,
timeouts, cancellations, and errors are all counted against the same set of
attempted actions.

Preflight reconstructs the origin, destination, active findings, policy, and any
bounded target information. Sentinel uses this context to classify capabilities
and protected-data categories, then derives redacted parameter and
approval-scope evidence. Missing URL context required by domain policy blocks
the proposal, while any other preflight error closes the transaction without
execution.

File uploads show why this live reconstruction matters, as Sentinel can inspect
only authorised, session-downloaded, or managed paths containing bounded,
regular UTF-8 text. Anything outside these conditions is unclassifiable and,
unless a higher-priority rule blocks it, is routed to a human step without
executing the upload. For a classifiable file, a keyed digest binds the
unrecorded content to approval scope. Sentinel repeats preflight after approval,
so changes to the file, target, origin, or policy are caught before execution.

\subsection{Risk, taint, and policy precedence}

The risk of a proposed action cannot be inferred from its name alone: a click
may submit a form or navigate, a URL may disclose a query across origins, and an
upload transfers a local file. Sentinel therefore evaluates the live target,
URL, destination, and any bounded content it can inspect. Effects outside the
BrowserUse integration remain outside Sentinel's claim.

Using that reconstructed context, the action guard identifies capabilities such
as navigation, page change, disclosure, file access, and code execution, then
considers them alongside the live origin, target, protected-data classes,
policy, and taint. This fuller view allows policy to prohibit
\texttt{evaluate} outright, for example, while sending a consequential click
for narrow review.

Taint remains tied to the origin that produced the finding, so it can persist
across steps without following the agent to unrelated origins or automatically
blocking every control on the same site. Sentinel can therefore judge each
proposed effect in context, even when legitimate and attacker-directed paths use
the same form.

\cref{tab:policy-order}. In enforce mode, hard prohibitions come before
human-step and approval paths, so an interactive response cannot weaken them.
Shadow records the same ordered decision without applying it, whereas off
bypasses the rules.

This distinction matters because only narrow approval can permit an agent
proposal to proceed; a human step leaves the action to the operator, an
observation incident offers no override, and a hard refusal remains final.

\subsection{Narrow approval and live revalidation}

An approval applies only to the proposal the operator reviewed, including its
origin, capabilities, taint, protected-data classes, target, and parameter or
content evidence. It normally applies once, although the server may offer an
\emph{Allow similar} grant that is confined to the current run, expires, and can
be used only a fixed number of times. Even after operator approval or a match to
an existing grant, Sentinel repeats the complete preflight using the latest
policy and browser state. If this fresh check finds a new block, requires a
human step, or discovers that the context has changed, Sentinel withholds the
action. Approval therefore applies to the opportunity at execution, not to an
earlier version of the page.

To prevent repeated interruptions, a per-run budget limits how often Sentinel
can ask for approval; once it is exhausted, the configured fallback either
requires a human step or blocks the proposal. Pending requests remain on the
server if the extension disconnects, and on reconnection the service returns
the current state and outstanding requests before continuing the event sequence.
A request card disappearing from the interface therefore never implies consent,
because only a response that reaches the server within the request's limits and
while it remains pending can change its state.

\subsection{Direct human control and resumption}

\Cref{tab:authority-taxonomy} defines the authority states; here, we follow how
control reaches the operator and how the agent resumes. First, \emph{Take over}
pauses further agent actions so the operator can interact with the page directly.
It does not approve a proposal or change policy, and an action already executing
cannot be recalled.

Second, the planner may invoke \texttt{request\_human\_control} for a login,
one-time code, CAPTCHA, payment, or private detail. Sentinel terminates the
remaining sequence and opens a server-owned wait that the model can neither
resolve nor use to acquire protected-value authority.

Third, policy forces the same handoff for recognised protected data,
unclassifiable uploads, the first governed page action on or targeting a
configured sensitive domain, or approval-budget fallback. Sentinel withholds the
proposal and records that it did not execute.

Each route resumes differently: during operator takeover, BrowserUse pauses at
its next control check and continues once control returns. A planner-requested
handoff ends the current action sequence, so the agent resumes with a fresh page
capture. A policy-enforced handoff records that the protected proposal did not
execute, and later proposals must pass through the guards again. In all three
cases, the next observation still passes through \texttt{GovernedLLM} and may
trigger an incident.

After a sensitive-domain handoff, Sentinel avoids repeating the same request
during that run, but this does not remove taint or create a broader exemption.
If the operator remains silent, cancels the request, or shuts down the run, the
unsafe action remains withheld.

\section{Audit and privacy}

Sentinel's audit explains outcomes without retaining raw transcripts. Each
action proposal produces an \texttt{attempted} record and a terminal record, so
blocks, denials, timeouts, cancellations, exceptions, and executor failures
share one denominator. Together, the records capture action class, verdict,
bounded risk and taint, origin, latency, and outcome; a separate enforcement
record gives the applicable rule and redacted reason.

Observation records use this pattern. Detection records store the score,
signals, and a run-keyed digest; sanitisation records show the path taken, how
many regions were affected, and the post-check result. Raw payloads and removed
spans are omitted. The digest links repeated detections within one run without
preserving content or creating a stable identifier.

Before storage or extension delivery, Sentinel again redacts task text, action
parameters, URLs, and free-text summaries. Extension events omit screenshots
and page titles; storing screenshots and free-form rationales is opt-in and
disabled by default. Even so, records distinguish proposal, execution,
intervention, and terminal outcome for trajectory analysis.

The Chrome extension described below presents these redacted events to the
operator, while enforcement and execution remain server-side.

\section{Chrome extension: operator-facing control plane}
\label{sec:control-plane}

\subsection{Client--server authority boundary}

Sentinel may pause a run for approval, direct human action, or review of an
observation. The Chrome extension makes these states visible and relays task,
control, policy, approval, and handover requests, but authority remains with the
service. The service owns the run, pending requests, audit, lifecycle, and
executor; it also rejects stale responses, keeps approvals narrowly scoped, and
revalidates actions before execution.

In the local prototype, Sentinel trusts the Chrome extension to relay the
operator's intent. A compromised client could answer an active request or change
policy, but could not call the executor directly, reuse stale authority, or
bypass service-side revalidation. Although these safeguards limit the client's
direct privileges, a compromised client could still influence the run. A
Manifest V3 worker and content script provide in-page controls, while the side
panel and dashboard communicate over HTTP and WebSocket; only the service can
change runtime state.

\subsection{Autonomous operation and browser ownership}

The side panel is the task-facing surface. Its composer starts a task, steers the
next step during a run, or begins a contextual follow-up after completion. The
panel reports the active model, remaining call budget, token use, current step,
and redacted agent exchange. \Cref{fig:governed-run} shows ordinary autonomous
operation before an intervention.

Intervention cards make the authority distinctions visible. An approval card

explains why the agent yielded and lets the operator mark the direct step

approval path; its re-check control requests a fresh capture from the service.

\subsection{Policy, Activity, and future HITL scope}

The dashboard separates next-task configuration from retrospective review. Its
Models tab configures the primary and fallback model for the next task.
Policies displays the active mode and configures domain and action rules,
protected data flows, approval behaviour, audit options, and budgets. Saved
policy changes apply at the next action boundary, even during a run, but cannot
decide an already pending request or bypass server validation.

Activity reconstructs completed runs from the service's history and event
trace. Its summary exposes policy mode, outcome, decision and intervention
counts, and wait and policy-check time; expansion reveals the service-sequenced
log. The timing split is descriptive accounting of recorded waits and
enforcement-processing time, not a matched off-mode counterfactual, and it omits
block-induced replanning. A non-allow decision can also carry an
\texttt{understood} marker that records whether its displayed reason was clear.
In the deterministic walkthrough both responses remain unset. The control is an
unevaluated instrument, not evidence of comprehension or usability.

from one walkthrough run. Panel~(a) shows the redacted approval card while the

These surfaces provide technical groundwork for a future HITL study, but do not

decision quality.

\section{Design synthesis}

The chapter's mechanisms implement R1--R5 as one chain: observation governance
supports R2; per-proposal mediation and policy implement R1 and R3; selective,
expiring authority supports R4; and paired redacted records support R5. If
observation handling misses or incompletely removes a hostile instruction, the
action guard still evaluates every proposal. Conversely, operator input cannot
override a hard prohibition.

Sentinel owns this governed path; the extension exposes its state and returns
bounded requests without acquiring execution authority. \Cref{chap:methodology}
next evaluates the hierarchy through mechanism checks, controlled AgentDojo
effects, browser-native WASP transfer, and control-plane walkthroughs.
