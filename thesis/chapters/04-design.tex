\chapter{Design and implementation}
\label{chap:design}

\section{Design principles}

The central design problem is to preserve the adaptability of a browser agent
without giving the same model final authority over the effects it proposes.
\systemname\ therefore wraps an existing planner and concentrates trusted
decisions at two explicit boundaries. Four principles follow.

\begin{enumerate}
  \item \textbf{Keep authority outside the acting model.} The model receives
  observations and tool outcomes, but only the middleware can reach the
  privileged executor.

  \item \textbf{Mediate both sides of the agent loop.} Observation handling
  reduces known hostile influence before inference; action handling constrains
  effects when hostile influence or ordinary model error remains.

  \item \textbf{Represent consent as bounded authority.} Approval is tied to
  reviewed live context and checked again before execution. Protected input is
  performed by the operator rather than approved for agent disclosure.

  \item \textbf{Fail closed and retain accountable outcomes.} Missing context,
  unresolved sanitisation, silence, timeout, stop, or malformed authority
  cannot become permission. Decisions remain inspectable without reproducing
  the sensitive content that caused them.
\end{enumerate}

\Cref{fig:architecture} shows the resulting division of responsibility.
BrowserUse continues to plan and recover from ordinary errors. Sentinel owns
the observation and action boundaries, the policy and authority state behind
them, and the audit record of each decision.

\section{Runtime composition}

The Python service composes these boundaries around BrowserUse rather than
forking its planner. For each task it creates a run-local context containing
budgets, origin-scoped findings, approval grants, intervention state, latency,
cancellation, and a fresh HMAC key. The runner then substitutes
\texttt{GovernedLLM} for the raw chat model and wraps the BrowserUse tool
registry with \texttt{GovernedTools}~\cite{zunic2026browseruse}. The model and
tool interface are unchanged; authority is added around them.

The supported observation boundary is deliberately text-only. Disabling vision
in BrowserUse does not itself prevent internal frame capture, so Sentinel
replaces the capture service with a discard implementation and removes images
from current-state and tool-result messages. This is a channel restriction, not
a claim that pixel-borne instructions have been neutralised: tasks requiring
visual grounding are excluded, and every evaluated interactive observation is
kept within the DOM/accessibility representation that Sentinel can inspect and
rewrite. Optional local visual trace retention remains separate from both the
model and extension paths.

Lifecycle control is part of the security boundary. Cancellation is checked
before and after an authority wait and again immediately before execution.
Approval and takeover deadlines expire before the outer agent-step timeout, so
Sentinel records a deliberate denial, timeout, or cancellation instead of
letting an unrelated upstream exception determine whether the action remains
pending.

\subsection{One governed agent step}

The two guards form one transaction around each model decision:

\begin{enumerate}[leftmargin=8mm]
  \item \textbf{Capture and classify.} BrowserUse produces the current
  DOM-derived state and bounded results from the preceding tool call.
  \texttt{GovernedLLM} separates trusted task instructions from
  browser-derived regions, normalises the latter, and removes sensitive URL
  metadata.

  \item \textbf{Rewrite and verify.} Enforce mode detects configured injection
  signals, rewrites attributable positive regions, reconstructs the exact
  provider message, and scans it again. If removal cannot be verified, Sentinel
  withholds the observation and pauses before any provider request. The model
  is never asked to adjudicate suspicious text that the enforcement layer could
  not make safe.

  \item \textbf{Plan.} The model receives only the governed representation and
  returns the same BrowserUse tool proposal it would produce without Sentinel.

  \item \textbf{Rebuild authority context.} \texttt{GovernedTools} records the
  attempt, then reads the current origin, target element, policy version,
  destination, protected-data classification, and sticky taint. The policy
  engine returns allow, block, approval, or takeover. Any interactive response
  is followed by the same live preflight.

  \item \textbf{Execute and close.} Only an allowed and still-valid proposal
  reaches the BrowserUse tool. Its success, failure, or cancellation closes the
  attempted/terminal audit pair before the next observation enters the loop.
\end{enumerate}

This ordering is intentionally asymmetric. Observation governance must precede
inference because an action cannot be undone merely by blocking a later tool;
the compromised plan may persist into subsequent turns. Action governance must
occur immediately before execution because the browser and policy can change
after inference. Sticky origin taint links the two boundaries without turning
it into a permanent global denial: it records that hostile content may already
have influenced the run, but the policy still evaluates the concrete proposed
effect and current target. The result is defence in depth with one owner for
each decision, rather than two independent mechanisms racing to interpret the
same event.

\section{Chrome extension control plane}
\label{sec:control-plane}

The architecture in \cref{fig:architecture} places the Chrome extension outside
the trusted runtime for a deliberate reason. It is the operator-facing
projection of Sentinel, not Sentinel itself. The Python service owns the run,
policy, pending requests, timers, audit sequence, and executor; the extension
turns a redacted subset of that state into four related surfaces: a task-centred
side panel, a minimal in-page ownership layer, a retrospective Activity view,
and model and policy configuration. The secondary Activity, policy, and
approval views are retained in \cref{fig:appendix-interface-evidence}; the main
argument begins with the state encountered during ordinary autonomous work.

\Cref{fig:governed-run} establishes that baseline. The in-page strip answers one
immediate question, namely who currently controls the browser, while the side
panel carries the richer task context: active model and policy mode, remaining
budget, current step, and the ongoing agent exchange. Showing this ordinary
state first is important because the intervention states introduced later are
changes in ownership within the same control protocol, not separate interfaces.

\begin{figure}[tbp]
\centering
\includegraphics[width=0.94\textwidth]{figures/interface-browser-and-panel-running-live.png}
\caption[Autonomous operation across page and side panel.]{Live implementation
state during ordinary autonomous operation. The browser page retains the
task's working context and a minimal ownership control; the side panel preserves
run state, budget, and agent interaction without becoming an authority source.}
\label{fig:governed-run}
\end{figure}

The side panel is organised around the current task rather than around raw log
records. An approval, human-step request, or security incident replaces the
ordinary progress controls with the one response that the server is waiting
for. The page layer remains intentionally sparse: it communicates ownership and
the command needed to return control, but never reproduces protected input,
attacker-controlled text, or the full audit record.

The dashboard serves a different temporal role. Policies and model settings
configure the next decision, whereas Activity reconstructs completed decisions
from paired attempted and terminal events. Its filters expose modes, outcomes,
authority demand, and security pauses; its run timeline places model, tool,
waiting, and incident intervals on a common clock. These are configuration,
debugging, and accountability functions. They do not move the reference monitor
into the browser.

That separation also governs failure. Side-panel and dashboard clients receive
a server snapshot followed by sequenced events. If a sequence gap appears, the
client discards its projection and reloads authoritative state. Reloading or
closing the extension neither approves nor cancels a waiting action, and a
vanished card is never interpreted as consent. Commands return through bounded
REST endpoints; only the server can validate them against the still-pending
request.

\section{Observation governance}
\label{sec:observation-governance}

\subsection{Untrusted regions and detection}

BrowserUse constructs model messages from current browser state, read state,
page extraction, and accumulated action results. Sentinel marks the
browser-derived regions and wraps later tool-result strings in a dedicated
untrusted region; forged copies of the wrapper syntax are escaped. The trusted
operator goal and system instructions are not scanned as page content.

Metadata receives mode-independent privacy treatment. HTTP(S) query strings
and fragments are omitted from model metadata. For non-web schemes such as
\texttt{data:}, \texttt{javascript:}, \texttt{blob:}, and \texttt{file:}, the
complete suffix is withheld from model, Activity, and trace boundaries. This
closes a less obvious disclosure path: unlike an ordinary web URL, the suffix
of a \texttt{data:} or \texttt{javascript:} URL may contain an entire document
or script, while a \texttt{file:} URL may reveal a local path. Treating that
suffix as routine navigation metadata would reproduce content that the
observation boundary was designed to withhold.

The detector is deterministic and combines several bounded signals, including
authority impersonation, task override, role reassignment, warning suppression,
exfiltration requests, forged protocol markup, and encoded instructions. A
finding records its score, severity, contributing signals, and source origin.
Crossing the configured threshold also taints that origin for the remainder of
the run: scrolling to a clean viewport does not erase the possibility that an
earlier observation already influenced the planner. Internally, Sentinel can
compare repeated content using a hash; public events expose a run-keyed digest
instead, preserving equality within one audit while preventing the same page
content from becoming a stable identifier across runs.

This signature design favours reproducibility and attributable removal over a
claim of semantic completeness. The evaluation therefore treats its scorecard
as component evidence and uses native end-to-end oracles for the main security
claim.

\subsection{Attributable sanitisation and its post-condition}

In enforce mode, a positive browser finding initiates targeted rewriting rather
than global string replacement. Line rules remove an attributable instruction
line or cluster; a bounded-window path handles attacks split across adjacent
accessibility-tree fragments. The wrapper then reconstructs the exact messages
that would be sent to the provider and runs the detector again. The resulting
state is one of:

\begin{description}[style=nextline,leftmargin=29mm]
  \item[\texttt{removed}] at least one attributable region changed and the
  reconstructed input is detector-clear;
  \item[\texttt{residual}] the input changed but remains detector-positive; or
  \item[\texttt{unattributable}] the finding could not be mapped to a region
  that could be removed safely.
\end{description}

Only \texttt{removed} satisfies the post-condition for silent continuation.
The model receives the rewritten observation rather than the attack plus a
warning. This design choice is grounded in the 9B WASP sequence reported in
\cref{chap:results}: warnings did not contain the measured attacks, whereas
successive sanitisation revisions reduced attacker-serving execution.

For a current browser observation, \texttt{residual} or
\texttt{unattributable} content is replaced before any provider call and opens
a server-owned security incident. The operator can inspect or change the page,
after which BrowserUse captures a fresh observation; the quarantined input is
never approved or reused. Bounded page-extraction and persistent historical
values use whole-value omission instead. Opening an interactive incident for a
nested or repeatedly stored value could deadlock the shorter subcall or produce
an incident loop, while omission keeps known unresolved text away from the
model.

Figure~\ref{fig:unresolved-observation} makes this negative guarantee visible.
The controlled page reproduces an accessibility shape that becomes
detector-positive only in aggregate. Sentinel cannot identify a bounded region
whose removal would satisfy the post-condition, so it withholds the observation
and pauses before the provider is called.

\FloatBarrier
\section{Action governance}
\label{sec:action-governance}

\subsection{The last responsible moment}

The action guard addresses a temporal problem that observation filtering alone
cannot solve. Between proposal and execution, a redirect may change the origin,
a re-render may replace the target element, a file may change, and live policy
may be edited. Sentinel therefore decides at the last responsible moment: after
the model has specified a concrete effect, but before the privileged tool is
invoked.

Each proposal opens a short transaction. Sentinel assigns a random action
identifier and records an \texttt{attempted} event before any risk-bearing
inspection. A guarded completion routine then closes that identifier with at
most one terminal outcome on every return or exception path. Failure to read a
URL, inspect a DOM target, scan a file, load policy, or contact an authority
client therefore remains a visible security outcome rather than disappearing
from the denominator.

Preflight reconstructs the authority context from live state. It reads the
current origin, bounded target semantics, destination, active injection
findings, and a fresh policy snapshot; classifies the action's capabilities and
protected-data categories; and derives redacted, run-keyed evidence for the
specific parameters and approval scope. If a verdict requires context that
cannot be obtained, Sentinel blocks. An absent observation is not treated as
evidence that no rule applies.

Files make this principle concrete. An upload transfers content, not merely a
pathname, so only BrowserUse-authorised, session-downloaded, or managed paths
are eligible for bounded inspection. Sentinel avoids symbolic links and
classifies regular UTF-8 text within the configured size limit. Remote, missing,
binary, oversized, unreadable, or otherwise unclassifiable content is handed to
the operator. The content itself is not logged; a keyed digest binds the
classified object to any approval scope. If an interactive decision is needed,
the complete preflight runs again after the response. Authority can permit the
reviewed opportunity, but it cannot preserve a stale target.

\subsection{Risk, taint, and amplified effects}

Risk is computed from both the proposed action and the context in which it was
formed. Capability labels capture the possible effect: navigation, typing,
upload, code execution, state change, or data disclosure. Live factors capture
what
matters about this particular proposal: its destination, target element,
protected-data classes, current policy, and whether untrusted content has
already influenced the run. This separation lets policy prohibit an inherently
dangerous capability such as code execution regardless of origin, while
reserving narrow approval for an otherwise permissible but consequential
action.

Injection taint is scoped to the origin that supplied the suspicious content
and persists for the run. Persistence matters because the relevant page may
leave the viewport after influencing the model; origin scope matters because a
finding does not make every control on that site malicious. In WASP, legitimate
and attacker-directed work can use the same GitLab or Reddit forms. A blanket
ban on all subsequent same-origin actions would therefore appear secure partly
by making the user's task impossible. Sentinel instead removes attributable
hostile content before planning, then applies effect-specific policy to the
concrete action that remains.

Some tools amplify modest-looking parameters into broader effects. A click can
submit a form or follow a redirect; a navigation can expose a query value to a
new origin; an upload transfers the contents of a local file rather than merely
its pathname. Sentinel therefore derives policy inputs from target semantics,
the live URL, destination, and bounded content inspection rather than trusting
the model's tool name alone. The navigation watchdog observes browser effects
that are not represented as an explicit \texttt{navigate} proposal. This does
not make the wrapper a complete browser reference monitor, but it closes the
documented paths through which the supported runner can produce privileged
effects.

\texttt{PolicyEngine.evaluate} is the central verdict method. Its effective
precedence is summarised in \cref{tab:policy-order}; a later interactive path
cannot weaken an earlier non-negotiable result.

In off mode, the policy returns allow and observation enforcement is disabled,
while redacted action audit remains. In shadow mode, Sentinel records the

wrapping, and metadata filtering remain active because they define the
supported interface rather than the experimental treatment.

Domain policy is also mirrored into BrowserUse's navigation watchdog. The
pre-action check governs explicit model proposals; the watchdog catches
redirects, pop-ups, link clicks, and page-script navigation that emerge as
browser effects. These observation points are complementary rather than
parallel sources of policy.

\section{Selective human authority}
\label{sec:human-authority}

Human involvement is not a single escalation level. It may confer narrow
authority on one proposal, move a protected step outside agent authority, or
help recover an observation that was never safe to show the model. Collapsing
these cases into a generic request for help would make the interface simpler
but the security meaning ambiguous. Sentinel therefore preserves the
distinctions in \cref{tab:authority-taxonomy}.

\begin{table}[htbp]
\centering
\caption{Distinct security meanings of operator involvement.}
\label{tab:authority-taxonomy}
\small
\begin{tabularx}{\textwidth}{@{}L{0.18\textwidth}L{0.29\textwidth}Y@{}}
\toprule
Runtime state & Trigger and response & Authority effect \\
\midrule
Hard refusal & Policy prohibits the effect; no approval control is offered &
The proposal cannot execute in the current run. \\
Narrow approval & Server requests allow once, bounded similar scope, or deny &
Only the reviewed proposal may proceed, and only after live preflight. \\
Human step & Agent requests help, or policy withholds a protected action &
The operator performs the step directly; the agent receives no authority to
handle the protected value. \\
Observation incident & Sanitisation cannot establish a clean post-condition &
The observation is quarantined; operator return requests a fresh capture rather
than approving the old one. \\
\bottomrule
\end{tabularx}
\end{table}

An approval request binds the action, origin, capabilities, taint, protected
data classes, target fingerprint, and applicable parameter or content digest.
A response may be one-use or a bounded similar-action grant only when the
server offered that scope. The grant remains run-local, expiring, and
use-capped. After a response or grant match, Sentinel repeats the complete
preflight: changed URL, DOM target, parameters, file content, policy, or scope
prevents execution. Approval therefore authorises a bounded opportunity to try
the proposal against current state, not the stale browser state shown on the
card.

\subsection{Three routes to human control}

The interface can place the browser in human control through three routes, but
they are not equivalent. First, the operator may select \emph{Take over} during
ordinary work. This is an operator-initiated pause for steering or direct
interaction, not an approval and not a policy override. The runner checks the
pause before subsequent actions and steps; an action already executing when the
operator clicks cannot be undone, so the interface does not claim instantaneous
cancellation.

Second, the planner may voluntarily invoke
\texttt{request\_human\_control}. Standing instructions direct it to do so for
login, one-time codes, CAPTCHAs, payment, or private details that require human
judgement or input. The request is still mediated by Sentinel: it terminates the
remaining action sequence and opens a server-owned wait. The model can request
help, but it cannot declare that help complete or use the request as permission
to handle the value itself.

Third, policy can force the same human-step protocol. If the proposed action
contains a recognised credential, access token, payment detail, private key,
protected free-text input, or unclassifiable upload, Sentinel withholds the
agent action before execution. The operator performs the step in the page. This
route records that policy, rather than the planner, initiated the transfer and
that the intercepted action was never executed.

All three routes converge on the same safe resumption rule. Giving control back
does not certify the resulting page as benign, clear origin taint, or revive the
agent's remaining actions. BrowserUse begins a new step from the current page;
the new DOM-derived state crosses \texttt{GovernedLLM}, where injection
detection, attributable sanitisation, and the clean post-condition apply again
before the next model call. If that new observation remains residual or cannot
be attributed safely, the run moves into the observation-incident path instead
of resuming the planner.

\Cref{fig:handover-projection} shows the second route in a natural protected
step. The agent reaches a local document portal whose account identifier is
already present but whose password is not available to the model. Rather than
inventing or typing a credential, it invokes
\texttt{request\_human\_control}. The persistent \emph{Take over} control is
the separate operator-initiated route and did not trigger the state shown. The
page preserves the password field the operator must complete, while the side
panel records the agent's reason, deadline, current URL, and return command.

\centering
\includegraphics[width=0.94\textwidth]{figures/interface-browser-and-panel-password-handover-live.png}

An observation incident has a different causal position. No action has been
derived from the quarantined input, the card contains no attacker text, and
there is no override path. Re-check releases only the wait for another capture.
Timeout, cancellation, shutdown, or an unavailable operator channel terminates
the unsafe continuation.

\section{Audit and privacy}

An audit trail should explain a security decision without recreating the
exposure it records. Sentinel therefore retains structured evidence rather
than a transcript of untrusted content. Each proposed browser effect opens an
\texttt{attempted} record before risk-bearing preflight and closes with exactly
one terminal outcome. Blocks, denials, timeouts, cancellations, exceptions,
and executor failures remain in the denominator even when execution never
begins. Together, the records preserve the action class, verdict, rule,
redacted reason, bounded risk and taint metadata, target origin, latency, and
outcome.

Observation records apply the same minimisation. Detection events retain a
score, signals, and a run-keyed digest; sanitisation events retain the branch,
affected-region counts, and post-check outcome. The original payload and
removed span are omitted. Keeping them would add little evidence of a clean
post-condition while preserving an attack instruction or protected value that
the boundary was meant not to propagate. The digest supports within-run
equality checks without creating a stable identifier or a second copy of the
observation. History and trace data are redacted again before reaching the
extension; screenshots and free-form rationale persistence remain off by
default; model summaries are treated as exposed outputs, not private
chain-of-thought.

The event stream supports operator inspection without moving authority into
the extension. Closing the panel cannot resolve a pending request; reconnecting
clients rebuild state from the service. Activity's pause counts and timing are
runtime telemetry. Its local \texttt{understood} markers deliberately prepare
for a future human-in-the-loop study, but the present walkthroughs contain no
participant comprehension protocol. They are therefore not analysed as a
human outcome. The interface can support inspection now without turning an
implementation trace into an unevaluated usability claim.

\section{From mechanism to evidence}

A coherent architecture is necessary, but it is not a security result.
Sentinel could mediate every action consistently and still fail if hostile
observations escaped detection, intervention came too late, or attacks vanished
only because legitimate work also became impossible. The design therefore
creates three evidential obligations: show that both guards operate as
specified, establish whether attacker-directed effects reach the executor or
their terminal objective, and measure what happens to the user's task at the
same time. Redacted audit explains the trajectory; native benchmark oracles
determine its outcome. Neither account is sufficient alone.

The next chapter evaluates those obligations in stages. Component replay
examines the guards directly, AgentDojo tests controlled end-to-end effects,
and WASP adds browser navigation and mutable page state. Together they test the
same research question without treating inactivity as security.
