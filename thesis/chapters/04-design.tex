\chapter{Design and implementation}
\label{chap:design}

\section{Design principles}

The central design problem is a separation of responsibilities. A browser agent
needs enough freedom to interpret a page, recover from errors, and choose its
next step. Yet the model that proposes that step should not also decide whether
it is safe to execute. \systemname\ therefore leaves planning to BrowserUse and
places two explicit enforcement boundaries around it. Four principles turn
that separation into a runtime design.

\begin{enumerate}
  \item \textbf{Keep authority outside the acting model.} The model receives
  observations and tool outcomes, but only the middleware can reach the
  privileged executor.

  \item \textbf{Mediate both sides of the agent loop.} The observation guard
  reduces known hostile influence before inference. The action guard then
  constrains the resulting effect, including when hostile influence or an
  ordinary planning error survives.

  \item \textbf{Represent consent as bounded authority.} Approval is tied to
  reviewed live context and checked again before execution. Protected input is
  withheld from the agent and entered directly by the operator.

  \item \textbf{Fail closed and retain accountable outcomes.} Missing context,
  unresolved sanitisation, silence, timeout, stop, or malformed authority
  cannot become permission. Decisions remain inspectable without reproducing
  the sensitive content that caused them.
\end{enumerate}

Together, these principles preserve the planner's useful flexibility while
making permission a property of the surrounding system. \Cref{fig:architecture}
shows how that division is realised. BrowserUse continues to plan and recover
from ordinary errors; Sentinel owns the observation and action guards, the
policy and authority state that informs them, and the audit record that explains
each decision.

Read from left to right, the figure follows intention to effect: a trusted task

as untrusted observations; the observation guard identifies, treats, and
verifies browser-derived regions before a governed representation reaches the
planner. Policy informs both guards, authority resolves bounded operator cases,
and audit records each decision. The extension presents this server-owned state
and returns bounded responses, but offers no route around either guard.

\section{Runtime composition}

The Python service inserts the guards without forking BrowserUse. Each task has
a run-local context for budgets, origin-scoped findings, grants, interventions,
latency, cancellation, and a fresh hash-based message authentication code
(HMAC) key. \texttt{GovernedLLM} replaces the raw model client, while
\texttt{GovernedTools} wraps the tool registry
~\cite{zunic2026browseruse}. BrowserUse retains its usual interfaces, but
observations cross the first wrapper and proposals cross the second.

This implementation governs a deliberately text-only model-input channel.
Sentinel removes screenshots and other images from current-state and tool-result
messages and replaces BrowserUse's remaining frame-capture service with a
discard implementation. The evaluated planner consequently operates on the
DOM/accessibility representation, which Sentinel can identify, inspect, and
rewrite. Instructions present only as pixels do not enter this supported model
channel; equally, tasks that require visual grounding fall outside the
evaluation. Extending Sentinel to a multimodal planner would therefore require
a separate guard for visual observations; DOM sanitisation alone would not
govern image content.

Sentinel also checks cancellation before and after an authority wait and again
immediately before execution. Approval and takeover deadlines expire before the
outer agent-step timeout, so a pending proposal closes with a deliberate denial,
timeout, or cancellation. Lifecycle control is part of the authority boundary.

\subsection{One governed agent step}

One agent step begins with captured state and ends with a terminal action
outcome:

\begin{enumerate}[leftmargin=8mm]
  \item \textbf{Capture.} BrowserUse supplies DOM-derived state and bounded
  results from the preceding tool call. \texttt{GovernedLLM} separates the
  trusted task from untrusted regions, normalises them, and removes sensitive
  URL metadata.

  \item \textbf{Sanitise and verify.} Enforce mode rewrites attributable
  findings, reconstructs the exact provider message, and scans it again. If the
  clean post-condition fails, Sentinel withholds the observation and pauses
  before the model request.

  \item \textbf{Plan.} The model receives the governed representation and
  returns an ordinary BrowserUse proposal. It describes an intended effect but
  carries no authority to produce it.

  \item \textbf{Rebuild authority.} \texttt{GovernedTools} records the attempt
  and reads the live origin, target, policy version, destination, protected-data
  class, and sticky taint. The policy engine returns allow, block, approval, or
  takeover. An operator response triggers the same preflight again.

  \item \textbf{Execute and close.} Only an allowed, still-valid proposal
  reaches the tool. Success, failure, or cancellation closes its audit pair
  before the next page state enters the loop.
\end{enumerate}

Observation governance comes first because a later block cannot erase a
compromised plan. Action governance comes last because page, target, and policy
may change after planning. Sticky origin taint connects the two moments without
replacing a live decision about the specific proposal. The following sections
develop the same loop through its control plane, guards, authority, and audit.

\section{Chrome extension control plane}
\label{sec:control-plane}

Runtime enforcement is useful to an operator only if its state and requests are
visible during browser work. The Chrome extension provides that control plane,
but it does not become another source of authority. Instead, the service owns
the run, policy, pending requests, timers, audit sequence, and executor, while
the extension presents a redacted view of that state. A Manifest V3 service
worker and content script provide the in-page ownership layer; the side panel
and dashboard receive service state through HTTP and WebSocket interfaces.
Consequently, the clients can display decisions and return bounded responses,
but they cannot create permission themselves.

That separation appears across three complementary surfaces. The side panel is
the task-facing surface: when no task is running, its composer starts a new
task; during a run, a new message steers the next agent step; and after
completion, it begins a contextual follow-up from the browser's current state.
It reports the active model, remaining call budget, token use, current step, and
redacted agent exchange. By contrast, the in-page strip provides an immediate
control cue over the browser: it shows at a glance whether the agent or the
operator currently controls it, with controls to take over, return control to
the agent, or stop the task. These interactions change browser ownership or
lifecycle state, not policy.
If Sentinel requests approval, hands over a protected step, or withholds an
observation, the panel presents the corresponding server-owned response card.
\Cref{fig:governed-run} shows the simpler starting point: ordinary autonomous
work before any such intervention.

\begin{figure}[tbp]
\centering
\includegraphics[width=0.94\textwidth]{figures/interface-browser-and-panel-running-live.png}
\caption{Ordinary autonomous operation.}
\label{fig:governed-run}
\end{figure}

This page-level interface remains deliberately sparse, keeping essential
control close to the browser without exposing protected input, hostile text,
or the full audit record. The dashboard serves a different purpose by
separating configuration from retrospective review. Its Models tab selects the
primary and fallback provider settings for the next task, whereas the Policies
tab both displays the active policy mode and configures domain and action rules,
protected data flows, approval behaviour, audit options, and budgets.
Saved~policy~changes take effect at the next action boundary, even during a run,
but cannot decide an already pending request or bypass server validation.
Activity then reconstructs what happened from paired attempted and terminal
events. An expanded run exposes its policy mode, outcome, decision and
intervention counts, recorded wait and policy-check time, and the corresponding
sequenced log.

Because any client may close or reconnect during a wait, its local view must be
reconstructible rather than authoritative. On each connection, the service
first sends a snapshot of current status, recent events, and pending authority
requests; sequenced events then keep that view current. A reconnecting client
therefore replaces its local projection from a fresh snapshot. Closing the
extension cannot resolve a waiting proposal, and a vanished card never counts
as consent. Only a bounded REST response for a request that remains pending can
change that state. With the operator-facing control plane established, the
design now turns to the observation that the planner is allowed to see.

\FloatBarrier
\section{Observation governance}
\label{sec:observation-governance}

\subsection{Untrusted regions and detection}

BrowserUse presents the planner with trusted task context alongside untrusted
browser state, page extractions, and earlier tool results. Sentinel therefore
locates browser-derived regions in the latest message and scans only their
contents; system instructions and the operator goal are not treated as page
text. Before a textual tool result enters BrowserUse's history, Sentinel also
escapes reserved protocol tags inside it and adds a dedicated untrusted wrapper.

This separation matters because a hostile page can print text that resembles
BrowserUse or Sentinel prompt structure. In enforce mode, \emph{boundary
neutralisation} escapes reserved tags only when they occur inside a recognised
untrusted region. The genuine outer wrappers and ordinary DOM tags remain
unchanged. Consequently, forged prompt syntax remains page data instead of
creating a trusted region or closing the real untrusted one.

Navigation metadata is also reduced before a provider call. Model-facing
browser state withholds page titles and replaces every HTTP(S) query string and
fragment wholesale. For non-web URLs, including \texttt{data:},
\texttt{javascript:}, \texttt{blob:}, and \texttt{file:}, only the scheme is
retained at model, event, Activity, and trace boundaries. This stronger rule is
necessary because the suffix may contain a document, script, local path, or
opaque identifier. General telemetry preserves safe HTTP(S) context but redacts
credentials and recognised sensitive values.

The detector then scores signals for explicit instruction override, authority
impersonation, role reassignment, secrecy or evasion, exfiltration, forged
markup, and encoded instructions. A strong signal can cross the threshold
alone; weaker cues must combine. Once it is crossed, the source origin remains
tainted for the run because the earlier content may already have influenced the
plan or history. The public event reports the score, severity, matched signals,
and origin, but replaces the detector's content hash with a run-keyed digest.
Repeated content can therefore be linked within one run without creating a
stable identifier across runs.

Deterministic patterns make findings repeatable and later removal attributable,
but an unfamiliar formulation may match no signal. Component replay therefore
tests detector coverage, while native end-to-end oracles test what the agent
ultimately does.

\subsection{Attributable sanitisation and its post-condition}

Once an observation is detector-positive, Sentinel must decide whether the
suspicious material can be removed without losing benign controls needed for
the task. With browser sanitisation enabled in enforce mode, it therefore
rewrites only content attributable to the finding. A line rule handles a
self-contained instruction, a bounded window covers an attack split across
neighbouring accessibility-tree fragments, and structured blocks provide a
third path.

Sentinel then rebuilds the exact messages intended for the provider and scans
them again. This second pass is essential: changing one region does not show
that another detected instruction has disappeared. The post-check consequently
produces one of three states:

\begin{description}[style=nextline,leftmargin=29mm]
  \item[\texttt{removed}] at least one attributable region changed and the
  reconstructed input is detector-clear;
  \item[\texttt{residual}] the input changed but remains detector-positive; or
  \item[\texttt{unattributable}] the finding could not be mapped to a region
  that could be removed safely.
\end{description}

These states determine whether a provider call may proceed. Under the full
configuration evaluated here, only \texttt{removed} continues. The planner
receives the rewritten observation without a detector warning, but its action
remains policy-gated. The WASP comparison in
\cref{chap:results} tests this treatment against the deliberately weaker
policy-only condition, which retains the detected content and warns the model.
Attacker-directed execution remained only in that comparator.

By contrast, a current browser observation classified as \texttt{residual} or
\texttt{unattributable} never reaches the model. Sentinel replaces it with a
fixed marker, opens a server-owned security incident, and waits for the
operator. Returning control then discards the held prompt and requires a fresh
page capture; it neither approves nor reuses the quarantined input.

Bounded page extractions and persistent tool results require a different
recovery path. The former runs inside a time-limited nested call, while the
latter remains in history after a page refresh. Pausing either could therefore
expire the nested call or reopen the same incident. Sentinel instead omits the
entire affected value, keeping unresolved content outside the model channel.

Figure~\ref{fig:unresolved-observation} shows the fail-closed branch. The
controlled page produces an accessibility structure that becomes
detector-positive only when its fragments are read together. No bounded removal
can then satisfy the post-condition, so Sentinel withholds the observation and
pauses before the provider is called. The unchanged 0/60 model-call budget
makes this pre-inference stop visible.

\caption{An unattributable observation withheld before inference.}

Once a governed observation reaches the planner, however, any resulting action
proposal still requires a separate decision at the action boundary.

\FloatBarrier
\section{Action governance}
\label{sec:action-governance}

\subsection{The last responsible moment}

Observation governance limits what the planner sees, but the browser can still
change before a proposal executes. A redirect may change the origin, a
re-render may replace the target, and a local file or policy may change. For
this reason, Sentinel decides at the last responsible moment: after the intended
effect is concrete, but before the privileged tool is called.

Each proposal also opens an auditable transaction. A random action identifier
and \texttt{attempted} record precede the fallible URL, DOM, file, risk, and
policy checks. A guarded completion routine then pairs every handled return or
exception with one terminal outcome and prevents duplicates. Blocks, denials,
timeouts, cancellations, execution errors, and executed actions therefore
remain visible in the same denominator.

Between those records, preflight reconstructs the live authority context: the
current origin and destination, active injection findings, a fresh policy
snapshot, and, for indexed clicks or inputs, bounded target attributes and text
where available. These best-effort semantics inform the decision; they do not
authorise it. Sentinel then classifies capabilities and protected-data
categories and derives redacted, run-keyed evidence for the parameters and any
approval scope. If active domain policy requires a current URL and none can be
obtained, the proposal is blocked. Other preflight exceptions end with a
terminal exception record rather than execution.

File upload shows why this reconstruction matters. Only BrowserUse-authorised,
session-downloaded, or managed paths are eligible for bounded inspection, and
Sentinel classifies only regular UTF-8 text within the configured size limit.
Remote, missing, binary, oversized, unreadable, or otherwise unclassifiable
content passes to the operator. The content is not logged; instead, a keyed
digest binds it to any approval scope. After an operator response, Sentinel
repeats the complete preflight, so a changed file, target, origin, or policy
must be judged again.

\subsection{Risk, taint, and amplified effects}

The action guard must look beyond a proposal's tool name. It labels possible
effects, including navigation, page changes, data disclosure, local-file
access, and code execution, and combines them with the live origins, target,
protected-data classes, policy, and earlier untrusted influence. The distinction
matters in practice, as policy can block \texttt{evaluate} outright while
holding an otherwise permitted click for narrow review when its target appears
consequential.

Origin-scoped injection taint carries that influence across steps because
suspicious text may leave the viewport after shaping the plan. Yet the finding
does not follow the agent to unrelated origins or automatically block every
control on the affected site. This distinction matters in WASP, where
legitimate and attacker-directed trajectories can use the same GitLab or Reddit
forms. Under the full treatment, Sentinel therefore removes attributable
hostile material, verifies the observation, and evaluates the concrete effect
of any proposal instead of imposing a blanket same-origin block that could also
prevent the user's task.

The concrete effect may also differ from the action name: a click can submit a
form or navigate, a URL can disclose a query value across origins, and an
upload transfers a local file. Sentinel therefore derives risk and policy
inputs from target semantics, the live URL, the destination, and bounded
content inspection. BrowserUse's watchdog adds coverage by checking requested
navigation, catching disallowed redirects, and closing new tabs that violate
domain policy. Together, these mechanisms cover the documented navigation
paths used by the supported BrowserUse runner. Effects outside that integration
boundary are beyond Sentinel's claim.

These inputs converge on \texttt{PolicyEngine.evaluate}. As
\cref{tab:policy-order} shows, hard prohibitions precede human-step and approval
paths, so a later interactive response cannot weaken them.

The operating modes determine whether these decisions alter the run. Off mode
returns allow and disables observation enforcement, although redacted action
audit remains. Shadow mode records the intervention that would have occurred
without applying it, whereas enforce mode applies both guards. The text-only
model channel, untrusted tool-result wrapping, and navigation-metadata
redaction remain active throughout because they define the supported interface,
not the experimental treatment.

Finally, a link, redirect, or page script can move the browser without an
explicit proposal. In enforce mode, Sentinel therefore mirrors its live domain
lists into BrowserUse's watchdog. The watchdog handles browser-level
navigation, but it is not a second general policy authority:
\texttt{PolicyEngine.evaluate} remains authoritative for explicit proposals.
When its decision requires human judgement or protected input, the transaction
moves into one of the authority paths described next.

\section{Selective human authority}
\label{sec:human-authority}

Human involvement answers three distinct runtime questions: may a reviewed
proposal proceed, must the operator perform a protected step, or may Sentinel
capture a fresh observation? Treating them as one generic request would obscure
the authority granted. Sentinel therefore separates them in server state and
interface, as summarised in \cref{tab:authority-taxonomy}.

\begin{table}[htbp]
\centering

\label{tab:authority-taxonomy}

\toprule

\midrule

The proposal cannot execute in the current run. \\

Only the narrow-approval row confers permission on an agent proposal. Its scope
binds the action, origin, capabilities, taint, protected-data classes, target
fingerprint, and applicable parameter or content digest. Permission applies
once unless the server offered a bounded similar-action scope, whose grants are
run-local, expiring, and use-capped. Sentinel repeats the full preflight after a
response or grant match. A changed URL, DOM target, parameter, file, or scope
invalidates the authority; a refreshed policy withholds execution only if it
blocks the action, requires a human step, or changes that scope. Approval thus
authorises the present opportunity, not frozen browser state.

\subsection{Three routes to human control}

The browser enters human control through three routes. First, the operator can
choose \emph{Take over} to steer the browser or interact directly. This command
pauses future agent actions without approving a pending proposal or changing
policy. An action already executing cannot be recalled, so the interface does
not claim instantaneous cancellation.

Second, the planner can invoke \texttt{request\_human\_control}. Standing
instructions reserve this route for login, one-time codes, CAPTCHAs, payment,
or private details requiring human judgement or input. Sentinel terminates the
remaining action sequence and opens a server-owned wait. The model may identify
the need for help, but it cannot resolve the request or acquire authority over
the protected value.

Third, policy can trigger the same protocol when the planner does not ask. A
proposal containing a recognised credential, access token, payment detail,
private key, protected free text, or unclassifiable upload is withheld before
execution, leaving the operator to perform the step in the page. The audit then
attributes the transfer to policy and records that the intercepted action never
ran.

Human return neither certifies the page as benign nor clears origin taint, but
resumption depends on the route. \emph{Take over} pauses future actions at
BrowserUse's next check. A planner request also terminates the remaining action
sequence and starts a new step from the current page. By contrast, a
policy-forced handover withholds the protected proposal while every later agent
action still passes through \texttt{GovernedTools} before execution. The next
model-facing page state crosses \texttt{GovernedLLM}; failure to establish the
clean post-condition enters the observation-incident path.

\Cref{fig:handover-projection} illustrates the second route at a protected
password step. The local document portal already contains an account identifier,
but the password is unavailable to the model. Instead of inventing or typing a
credential, the planner invokes \texttt{request\_human\_control}. The page
retains the field that the operator must complete, while the side panel records
the reason, deadline, current URL, and return command. The state shown was
initiated by the planner's request, not by the separate operator-initiated
\emph{Take over} route.

An observation incident sits earlier in the loop than all three handover
routes. No proposal has been derived from the quarantined input, its card
contains no attacker text, and the interface offers no override. Re-checking
only releases the wait for a fresh capture. Timeout, cancellation, shutdown, or
an unavailable operator channel ends that unsafe continuation. In every case,
the audit trail must explain the transition without recreating the content that
made it sensitive.

\section{Audit and privacy}

The audit design follows a simple tension: a record must explain the security
decision, but should not reproduce the exposure it describes. Sentinel therefore
stores structured evidence instead of transcripts of untrusted content. Every
proposed browser effect opens an \texttt{attempted} record before risk-bearing
preflight and closes with exactly one terminal outcome. Blocks, denials,
timeouts, cancellations, exceptions, and executor failures remain in the
denominator even when execution never begins. The paired records retain the
action class, verdict, bounded risk and taint metadata, target origin, latency,
and outcome. When policy reaches a verdict, the accompanying enforcement
decision adds its rule and redacted reason.

Observation events apply the same principle. A detection record keeps its
score, signals, and run-keyed digest; a sanitisation record keeps the branch,
number of affected regions, and post-check outcome. The original payload and
removed span are omitted because retaining them would preserve an attack
instruction or protected value without strengthening evidence that the
post-condition was satisfied. The digest still supports equality checks within
the run without creating a stable identifier or another copy of the
observation. History and trace data are redacted again before they reach the
extension. Before storage or extension delivery, Sentinel also redacts exposed
task, action, URL, and summary fields. Extension-bound events omit screenshots
and page titles, while persistent screenshot and free-form model-rationale
retention are opt-in and disabled by default.

reconnecting client rebuilds its view from the service. Activity's pause counts
and timing are runtime telemetry used to reconstruct the sequence of decisions
and outcomes. It also provides a per-decision \texttt{understood} marker through
which the operator can record whether the reason for an intervention was clear.
Although that marker is not evaluated in this dissertation, it provides one
initial instrument that a future human-in-the-loop study could refine alongside
validated measures of comprehension, decision quality, and intervention burden.

\section{From mechanism to evidence}

The completed loop defines what Sentinel is supposed to do, but architecture
alone cannot establish a security result. Both guards could execute exactly as
specified while an unseen formulation passes detection, a decision arrives too
late, or legitimate work collapses alongside the attack. The design therefore
creates three evidential obligations: verify the guards directly, determine
whether attacker-directed proposals reach execution or achieve the attacker's
terminal objective, and measure task utility alongside those security outcomes.
Redacted audit explains the trajectory, while native benchmark oracles determine
its final state; each answers a question the other cannot.

Chapter~\ref{chap:methodology} turns those obligations into an evidence chain.
Component replay exercises the guards directly, AgentDojo tests controlled
end-to-end effects, and WASP adds browser navigation, observations, and
replanning over mutable applications. Their common purpose is to determine
whether enforcement reduces evaluated violations while preserving useful
autonomy without mistaking an inactive agent for a secure one.
